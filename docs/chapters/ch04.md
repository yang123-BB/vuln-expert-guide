## 4.1 虚拟内存管理机制

### 4.1.1 虚拟内存概述

虚拟内存是现代操作系统最核心的抽象之一，它为每个进程提供了一致的、隔离的地址空间视图。对于漏洞挖掘而言，理解虚拟内存机制至关重要，因为绝大多数内存破坏漏洞都涉及到对虚拟内存的误解或滥用。

**核心概念**：

- **虚拟地址（Virtual Address）**：程序看到的地址，通常是线性地址空间
- **物理地址（Physical Address）**：实际内存硬件上的地址
- **页（Page）**：虚拟内存管理的基本单位，典型大小为4KB
- **页帧（Page Frame）**：物理内存中与页对应的单位
- **页表（Page Table）**：用于虚拟地址到物理地址的转换

```
┌─────────────────┐
│  虚拟地址空间    │  ← 每个进程独立的视图
│  (0x00000000    │
│   ~             │
│   0xFFFFFFFF)   │
└────────┬────────┘
         │ MMU 转换
         ▼
┌─────────────────┐
│  物理内存        │  ← 实际硬件内存
│  (RAM)          │
└─────────────────┘
```

### 4.1.2 分页机制详解

#### x86-32 分页（32位系统）

在32位x86架构上，经典的分页机制使用两级页表：

**地址结构**（4KB页面）：
- 位31-22：页目录项索引（PDE，10位，1024个项）
- 位21-12：页表项索引（PTE，10位，1024个项）
- 位11-0：页内偏移（12位，4096字节）

```
虚拟地址（32位）
┌──────────────────────────────────────────────────────┐
│ 31 22  │ 21   12 │ 11      0                        │
│────────│─────────│──────────────────────────────────│
│  PDE   │   PTE   │         页内偏移                  │
│ 索引   │   索引  │                                  │
│ (10位) │  (10位) │         (12位)                   │
└──────────────────────────────────────────────────────┘
         │          │
         ▼          ▼
    ┌─────────┐ ┌─────────┐
    │页目录项 │ → │页表项   │ → 物理页帧
    └─────────┘ └─────────┘
```

**页目录项（PDE）和页表项（PTE）结构**：

```
31                                                                 0
┌───────────────────┬────┬────┬────┬────┬────┬────┬────┬────┬──────┐
│   物理基址(20位)   │AVAIL│G   │PS  │D   │A   │PCD │PWT │U/S │R/W │P │
│                   │    │    │    │    │    │    │    │    │    │  │
└───────────────────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴──┘
```

关键标志位：
- **P（Present）**：该页是否在物理内存中
- **R/W（Read/Write）**：0=只读，1=可读写
- **U/S（User/Supervisor）**：0=内核态，1=用户态可访问
- **A（Accessed）**：是否被访问过（用于页面置换算法）
- **D（Dirty）**：是否被写过（仅PTE）

#### x86-64 分页（64位系统，4级页表）

64位系统扩展了地址空间，使用4级页表（有时是5级）：

**48位地址结构**（典型x86-64）：
- 位47-39：PML4表索引（9位）
- 位38-30：PDPT索引（9位）
- 位29-21：PD索引（9位）
- 位20-12：PT索引（9位）
- 位11-0：页内偏移（12位）

```
虚拟地址（64位，实际只用48位）
┌──────────┬──────────┬──────────┬──────────┬──────────┬─────────┐
│63    48  │47   39   │38   30   │29   21   │20   12   │11     0 │
│──────────│──────────│──────────│──────────│──────────│─────────│
│ 符号扩展  │  PML4    │   PDPT   │    PD    │    PT    │ 偏移   │
│  (16位)  │  (9位)   │   (9位)  │   (9位)  │   (9位)  │ (12位) │
└──────────┴──────────┴──────────┴──────────┴──────────┴─────────┘
                         │          │          │         │
                         ▼          ▼          ▼         ▼
                    ┌────────┐ ┌────────┐ ┌────────┐ ┌──────┐
                    │ PML4E  │→│ PDPTE  │→│  PDE   │→│ PTE  │ → 物理页
                    └────────┘ └────────┘ └────────┘ └──────┘
```

### 4.1.3 TLB（Translation Lookaside Buffer）

TLB是CPU内部的高速缓存，用于缓存最近的虚拟地址到物理地址的转换结果。

**为什么需要TLB？**
每次内存访问都需要遍历页表（1-4次内存访问），这会导致严重的性能损失。TLB将常用转换缓存起来，使大多数内存访问无需页表遍历。

**TLB结构**：
- **VPN（Virtual Page Number）**：虚拟页号（标签）
- **PFN（Physical Frame Number）**：物理页帧号（数据）
- **标志位**：有效位、用户/内核、读/写/执行权限等

**TLB刷新**：
- **invlpg指令**：使单个TLB项无效
- **写入CR3寄存器**：刷新整个TLB（上下文切换时）
- **PCID（Process Context Identifier）**：x86-64的特性，允许TLB项携带进程标签，减少上下文切换时的TLB刷新

**漏洞挖掘视角**：
TLB与CPU缓存的交互是侧信道攻击（如Spectre、Meltdown）的关键。攻击者可以利用TLB状态推断内存访问模式。

### 4.1.4 页表遍历与CR3寄存器

**CR3寄存器**：
CR3是x86/x86-64架构中的控制寄存器，存储当前进程的页目录基址（物理地址）。

```
CR3寄存器结构（32位PAE或64位）
┌──────────────────────────┬────┬────┬────┬───────────┐
│   页目录基址（20/28位）   │PCD │PWT │   保留     │
└──────────────────────────┴────┴────┴───────────────┘
```

- **PCD（Page-Level Cache Disable）**：禁用页级缓存
- **PWT（Page-Level Write-Through）**：页级写穿策略

**页表遍历过程**（以x86-64为例）：

1. MMU接收虚拟地址VA
2. 用VA[47:39]索引PML4表（基址在CR3）
3. 读取PML4E，获取PDPT物理地址
4. 用VA[38:30]索引PDPT，读取PDPTE
5. 用VA[29:21]索引PD，读取PDE
6. 用VA[20:12]索引PT，读取PTE
7. PTE中的物理基址 + VA[11:0] = 物理地址

**如果在遍历过程中发现P=0（页不在内存）**：
- 触发**缺页异常（#PF，Page Fault）**
- 操作系统异常处理程序将页从磁盘加载到物理内存
- 更新页表项，重新执行触发异常的指

**漏洞相关**：
- 内核漏洞常涉及不正确的页表管理
- 用户态程序可以通过缺页异常探测内存布局
- 某些攻击（如L1 Terminal Fault）利用页表遍历过程中的竞态条件

## 4.2 进程内存布局

### 4.2.1 Linux进程内存布局（x86-32）

典型的Linux 32位进程内存布局（高地址到低地址）：

```
0xFFFFFFFF  ┌─────────────────────────────────────┐
            │         内核空间 (1GB)              │
0xC0000000  └─────────────────────────────────────┘
            ┌─────────────────────────────────────┐
            │        栈 (Stack)                   │
            │        ↓ 向低地址增长               │
            │                                     │
            │          (空白区域)                  │
            │                                     │
            │        堆 (Heap)                    │
            │        ↑ 向高地址增长               │
            ├─────────────────────────────────────┤
            │        BSS段                        │
            │    (未初始化全局变量)                │
            ├─────────────────────────────────────┤
            │        数据段 (.data)                │
            │    (已初始化全局变量)                │
            ├─────────────────────────────────────┤
            │        代码段 (.text)                │
            │        (程序指令)                    │
0x08048000  └─────────────────────────────────────┘
            ┌─────────────────────────────────────┐
            │        NULL陷阱页 (不可访问)         │
0x00000000  └─────────────────────────────────────┘
```

### 4.2.2 各段详解

#### 代码段（.text）

- **内容**：程序的机器指令
- **权限**：通常R-X（可读、可执行、不可写）
- **加载地址**：通常由链接器确定，Linux下典型为0x08048000（32位）或0x400000（64位）
- **漏洞相关**：
  - 缓冲区溢出覆盖返回地址时，常跳转到.text中的gadget
  - ROP攻击依赖.text中的代码片段
  - 代码注入需要可写的代码段（现代系统已禁止）

#### 数据段（.data）

- **内容**：已初始化的全局变量和静态变量
- **权限**：通常RW-（可读、可写、不可执行）
- **示例**：
  ```c
  int global_var = 42;        // 在.data段
  static int static_var = 100; // 在.data段
  ```

#### BSS段（.bss）

- **内容**：未初始化的全局变量和静态变量
- **权限**：通常RW-
- **特点**：不占用可执行文件空间（只是记录大小），运行时初始化为0
- **示例**：
  ```c
  int uninit_global;        // 在.bss段
  static int uninit_static; // 在.bss段
  ```

#### 堆（Heap）

- **内容**：动态分配的内存（malloc/new）
- **权限**：通常RW-
- **增长方向**：向高地址增长
- **管理**：由堆管理器（如glibc的ptmalloc2）管理
- **漏洞相关**：
  - 堆溢出（heap overflow）
  - Use-after-free
  - Double free
  - 堆元数据破坏

#### 栈（Stack）

- **内容**：局部变量、函数参数、返回地址
- **权限**：通常RW-
- **增长方向**：向低地址增长（x86/x86-64）
- **大小限制**：可通过ulimit -s查看/设置
- **漏洞相关**：
  - 栈溢出（stack overflow）
  - 返回地址覆盖
  - 栈上的格式化字符串攻击

### 4.2.3 Linux进程内存布局（x86-64）

64位系统的地址空间大大增加：

```
0xFFFFFFFFFFFFFFFF  ┌─────────────────────────────────────┐
                    │         内核空间 (128TB)            │
0xFFFF800000000000  └─────────────────────────────────────┘
                    ┌─────────────────────────────────────┐
                    │         保留区域                     │
0x00007FFFFFFFFFFF  └─────────────────────────────────────┘
                    ┌─────────────────────────────────────┐
                    │        栈 (Stack)                   │
                    │        ↓ 向低地址增长               │
                    │                                     │
                    │          (空白区域)                  │
                    │                                     │
                    │        内存映射区域 (mmap)           │
                    │     (共享库、匿名映射等)              │
                    │                                     │
                    │          (空白区域)                  │
                    │                                     │
                    │        堆 (Heap)                    │
                    │        ↑ 向高地址增长               │
                    ├─────────────────────────────────────┤
                    │        BSS段                        │
                    ├─────────────────────────────────────┤
                    │        数据段 (.data)                │
                    ├─────────────────────────────────────┤
                    │        代码段 (.text)                │
0x0000000000400000  └─────────────────────────────────────┘
                    ┌─────────────────────────────────────┐
                    │        NULL陷阱页                   │
0x0000000000000000  └─────────────────────────────────────┘
```

**关键变化**：
1. 地址空间从4GB扩展到128TB（x86-64的48位地址）
2. 栈和mmap区域从两端向中间增长，减少碎片
3. 共享库加载到内存映射区域，而非固定的低地址

### 4.2.4 查看进程内存布局

**使用/proc文件系统**：

```bash
# 查看当前进程的内存映射
cat /proc/self/maps

# 输出示例
00400000-00401000 r-xp 00000000 08:01 123456  /path/to/binary
00600000-00601000 r--p 00000000 08:01 123456  /path/to/binary
00601000-00602000 rw-p 00001000 08:01 123456  /path/to/binary
```

**每列含义**：
1. 地址范围
2. 权限（r=读, w=写, x=执行, p=私有, s=共享）
3. 文件偏移
4. 设备号
5. inode号
6. 映射文件名

**使用GDB**：

```gdb
# 查看内存映射
(gdb) info proc mappings

# 查看特定地址的内容
(gdb) x/10x $rsp  # 查看栈顶
(gdb) x/10i $rip  # 查看当前指令
```

## 4.3 栈帧结构与函数调用

### 4.3.1 x86-32 栈帧

**函数调用时的栈布局**（调用链：main → func）：

```
高地址
│
├─────────────────────────────────┐
│     调用者main的栈帧             │
│  ┌───────────────────────────┐  │
│  │  局部变量                  │  │
│  ├───────────────────────────┤  │
│  │  保存的EBP (调用者的EBP)   │ ← EBP of main
│  ├───────────────────────────┤  │
│  │  返回地址 (main的EIP)      │ ← 被func返回时弹出
│  └───────────────────────────┘  │
├─────────────────────────────────┤ ← ESP after prologue
│     被调用者func的栈帧           │
│  ┌───────────────────────────┐  │
│  │  局部变量                  │  │
│  ├───────────────────────────┤  │
│  │  保存的EBP (main的EBP)    │ ← EBP of func
│  ├───────────────────────────┤  │
│  │  返回地址 (func的EIP)      │ │
│  └───────────────────────────┘  │
├─────────────────────────────────┤
│                                 │
低地址                            ← ESP当前位置
```

**函数序言（Prologue）**：
```asm
push ebp        ; 保存调用者的EBP
mov ebp, esp    ; 设置新的EBP
sub esp, N      ; 为局部变量分配N字节空间
```

**函数结尾（Epilogue）**：
```asm
mov esp, ebp    ; 释放局部变量空间
pop ebp         ; 恢复调用者的EBP
ret             ; 弹出返回地址，跳回调用者
```

### 4.3.2 x86-64 栈帧与调用约定

x86-64引入了寄存器传参，改变了栈的使用方式。

**System V AMD64 ABI调用约定**（Linux、macOS等）：
- 前6个整数/指针参数：RDI, RSI, RDX, RCX, R8, R9
- 前8个浮点参数：XMM0-XMM7
- 额外参数：压入栈中（从右到左）
- 返回值：RAX（整数）、XMM0（浮点）

**栈帧布局**（x86-64）：

```
高地址
│
├─────────────────────────────────┐
│     调用者的栈帧                 │
│  ┌───────────────────────────┐  │
│  │  ...                      │  │
│  └───────────────────────────┘  │
├─────────────────────────────────┤
│     参数7、参数8...（如果有）     │ ← 由调用者压栈
├─────────────────────────────────┤
│     返回地址                     │ ← 由call指令压栈
├─────────────────────────────────┤ ← RBP of callee (通常省略)
│     被调用者的栈帧                │
│  ┌───────────────────────────┐  │
│  │  （可能）保存的寄存器       │  │
│  ├───────────────────────────┤  │
│  │  局部变量                  │  │
│  └───────────────────────────┘  │
├─────────────────────────────────┤
│     函数调用时参数7、8...的空间   │ ← 为调用其他函数预留
├─────────────────────────────────┤
│                                 │
低地址                            ← RSP当前位置
```

**关键变化**：
1. 许多参数通过寄存器传递，减少栈使用
2. 许多函数使用**帧指针省略（FPO）**，不保存EBP/RBP，直接用RSP寻址局部变量
3. 栈必须16字节对齐（SSE指令要求）

### 4.3.3 栈溢出原理

**经典的栈溢出漏洞**：

```c
#include <stdio.h>
#include <string.h>

void vulnerable() {
    char buffer[64];
    gets(buffer);  // 不安全的函数，无边界检查
}

int main() {
    vulnerable();
    return 0;
}
```

**编译与运行（关闭保护）**：
```bash
gcc -m32 -z execstack -fno-stack-protector -no-pie -o vuln vuln.c
```

**栈溢出过程**：

```
初始栈状态（调用vulnerable后）
┌─────────────────────────────────┐
│  buffer[63]                     │
│  ...                            │
│  buffer[0]                      │
├─────────────────────────────────┤ ← EBP of main (保存的EBP)
│  保存的EBP                       │
├─────────────────────────────────┤ ← 返回地址 (main中call vulnerable的下一条指令)
│  返回地址                        │
└─────────────────────────────────┘ ← ESP

输入超长字符串后（例如72个'A' + "BBBB"）
┌─────────────────────────────────┐
│  'A' * 64                       │
├─────────────────────────────────┤
│  'A' * 4 (覆盖保存的EBP)         │
├─────────────────────────────────┤
│  'B' * 4 = 0x42424242 (覆盖返回地址) │ ← 函数返回时跳转到0x42424242！
└─────────────────────────────────┘
```

**漏洞利用**：
1. 攻击者控制返回地址
2. 跳转到shellcode（如果栈可执行）
3. 或跳转到现有代码（ROP）

### 4.3.4 栈保护机制：Stack Canary

**原理**：
在函数序言中，在返回地址前插入一个随机值（canary），函数返回前检查该值是否被修改。

**GCC实现**：
```c
// 编译时启用stack protector
gcc -fstack-protector          // 为有数组的函数启用
gcc -fstack-protector-strong    // 为更多函数启用（推荐）
gcc -fstack-protector-all       // 为所有函数启用
gcc -fno-stack-protector        // 禁用
```

**栈布局（启用canary后）**：

```
┌─────────────────────────────────┐
│  局部变量                        │
├─────────────────────────────────┤
│  Stack Canary (随机值)          │ ← 在保存的EBP之前
├─────────────────────────────────┤
│  保存的EBP                       │
├─────────────────────────────────┤
│  返回地址                        │
└─────────────────────────────────┘
```

**检查代码**（函数返回前）：
```asm
mov    rax, QWORD PTR [rbp-0x8]  ; 读取canary
xor    rax, QWORD PTR fs:0x28    ; 与原始值比较（fs:0x28存储原始canary）
call   __stack_chk_fail          ; 如果不匹配，调用失败处理函数
```

**绕过技术**：
1. **信息泄露**：泄露canary值（如格式化字符串漏洞）
2. **brute force**：如果canary可预测或程序重启后canary不变（某些旧系统）
3. **覆盖fs:0x28**：需要任意写原语
4. **部分覆盖**：如果canary有NULL字节（x86-64的canary通常以NULL字节开头），可能部分覆盖

## 4.4 堆内存管理

### 4.4.1 堆管理器概述

**用户态堆管理器**：
- **glibc (ptmalloc2)**：Linux最常用的堆管理器
- **jemalloc**：Firefox、FreeBSD使用
- **tcmalloc**：Google的堆管理器
- **Windows堆管理器**：Windows系统的堆管理

**内核态内存分配**：
- Linux：`kmalloc`, `vmalloc`
- Windows：`ExAllocatePool`

本章重点介绍**ptmalloc2**（glibc的malloc实现）。

### 4.4.2 ptmalloc2 基础

**主要函数**：
```c
void *malloc(size_t size);       // 分配内存
void free(void *ptr);            // 释放内存
void *calloc(size_t n, size_t size); // 分配并清零
void *realloc(void *ptr, size_t size); // 重新分配
```

**堆块结构**：

ptmalloc2管理的每个堆块都有一个元数据头（chunk header）：

```
┌────────────────────────────────────────────────────────────────┐
│  size_t mchunk_prev_size (仅当前一个块空闲时有效)              │ ← 如果前一个块空闲，此字段存在
├────────────────────────────────────────────────────────────────┤ ← 用户得到的指针位置 (mem)
│  size_t mchunk_size          │A│M│P                           │ ← 当前块大小 + 标志位
├────────────────────────────────────────────────────────────────┤
│  用户数据开始...                                               │
│  ...                                                           │
│  (size - 2*SIZE_SZ 字节)                                      │
└────────────────────────────────────────────────────────────────┘
```

**mchunk_size字段**：
- 低3位用作标志位（因为堆块对齐到8或16字节，低3位总是0）
- **P（PREV_INUSE）**：前一个块是否在使用中（1=使用中，0=空闲）
- **M（IS_MMAPPED）**：是否通过mmap分配
- **A（NON_MAIN_ARENA）**：是否属于非主arena

**重要宏**：
```c
#define PREV_INUSE 0x1
#define IS_MMAPPED 0x2
#define NON_MAIN_ARENA 0x4

#define chunk2mem(p)   ((void*)((char*)(p) + 2*SIZE_SZ))
#define mem2chunk(mem) ((mchunkptr)((char*)(mem) - 2*SIZE_SZ))
#define chunksize(p)   ((p)->mchunk_size & ~(SIZE_BITS))
```

### 4.4.3 空闲堆块管理：bins

ptmalloc2将空闲堆块组织到多个bin中，以便快速分配和合并。

**bin的分类**：

1. **fastbin**（单链表）
   - 存放小堆块（64位下≤128字节，含元数据）
   - 数量：10个fastbin（x86-64）
   - 特点：LIFO（后进先出），不合并（提高速度）
   - 漏洞利用：double free、fastbin attack

2. **smallbin**（双链表）
   - 存放大小<1024字节（64位）的堆块
   - 数量：62个smallbin
   - 特点：FIFO（先进先出），精确匹配大小

3. **largebin**（双链表）
   - 存放大小≥1024字节的堆块
   - 数量：63个largebin
   - 特点：同一个bin中的块大小不同，按大小排序

4. **unsorted bin**（双链表）
   - 存放刚释放但尚未分类的堆块
   - 数量：1个
   - 作用：作为缓存，减少分类开销

5. **tcache**（Thread Local Cache，glibc 2.26+）
   - 每个线程独立的缓存
   - 数量：64个tcache bin
   - 特点：单链表，LIFO，不检查完整性
   - 漏洞利用：tcache poisoning

**fastbin结构示例**（x86-64，8字节元数据）：

```
fastbin[0] → 32字节堆块 → 32字节堆块 → NULL
fastbin[1] → 48字节堆块 → NULL
...
fastbin[9] → 128字节堆块 → 64字节堆块 → NULL
```

### 4.4.4 常见堆漏洞

#### 1. 堆溢出（Heap Overflow）

```c
#include <stdlib.h>
#include <string.h>

struct data {
    char name[32];
    int age;
};

int main() {
    struct data *d1 = malloc(sizeof(struct data));
    struct data *d2 = malloc(sizeof(struct data));
    
    // 溢出d1，覆盖d2的元数据
    memset(d1->name, 'A', 64);  // 溢出！
    
    free(d2);  // 可能崩溃或执行任意代码
    return 0;
}
```

#### 2. Use-After-Free（UAF）

```c
#include <stdlib.h>

struct object {
    void (*func)();
    char data[32];
};

int main() {
    struct object *obj = malloc(sizeof(struct object));
    obj->func = (void (*)())0xdeadbeef;  // 设置函数指针
    
    free(obj);  // 释放
    
    // 此时obj仍然指向已释放的内存！
    obj->func();  // Use-After-Free：调用可能已经损坏的函数指针
    return 0;
}
```

#### 3. Double Free

```c
#include <stdlib.h>

int main() {
    void *p = malloc(32);
    free(p);
    free(p);  // Double Free！可能导致任意代码执行
    return 0;
}
```

#### 4. 堆元数据破坏

攻击者通过溢出或其他方式修改堆块的元数据（size字段、fd/bk指针等），在后续malloc/free时实现任意地址读写。

**House of Force**、**House of Spirit**、**House of Lore**等是经典的堆利用技术。

### 4.4.5 tcache详解（glibc 2.26+）

tcache（Thread Local Cache）是glibc 2.26引入的优化，大幅提升了多线程性能，但也引入了新的利用方式。

**tcache_entry结构**：
```c
typedef struct tcache_entry {
    struct tcache_entry *next;  // 单链表指针
} tcache_entry;
```

**tcache_perthread_struct**：
```c
typedef struct tcache_perthread_struct {
    char counts[TCACHE_MAX_BINS];  // 每个bin中的块数量
    tcache_entry *entries[TCACHE_MAX_BINS];  // 每个bin的链表头
} tcache_perthread_struct;
```

**tcache特点**：
1. 每个线程独立，无锁
2. 最多缓存64个bin，每个bin最多7个块（可配置）
3. **不检查完整性**：可以多次free同一块（tcache poisoning）
4. **分配时优先从tcache取**

**tcache poisoning示例**：

```c
// 假设可以溢出修改tcache中的next指针
tcache_entry *entry = tcache->entries[bin_index];
entry->next = target_address - 0x10;  // 指向目标地址（减去元数据大小）

// 接下来的两次malloc：
// 第一次：返回正常的tcache块
// 第二次：返回target_address！可以读写任意地址
```

## 4.5 现代内存保护机制

### 4.5.1 ASLR（Address Space Layout Randomization）

**原理**：
ASLR随机化进程关键区域的加载地址，使攻击者难以预测目标地址。

**随机化的区域**：
1. **栈地址**：每次执行随机化
2. **堆地址**：每次执行随机化
3. **共享库加载地址**：每次系统启动随机化（或每次执行）
4. **可执行文件基址**：如果编译为PIE（Position Independent Executable）

**查看ASLR状态**（Linux）：
```bash
cat /proc/sys/kernel/randomize_va_space
# 0 = 关闭
# 1 = 保守模式（部分随机化）
# 2 = 全随机化（默认）
```

**ASLR级别**：
- **0**：禁用ASLR
- **1**：保留随机化（conservative），随机化栈、mmap、共享库，但不随机化可执行文件基址（除非PIE）
- **2**：全随机化（full），包括可执行文件基址（需要PIE）

**绕过技术**：

1. **信息泄露**：
   ```c
   // 通过格式化字符串、越界读等泄露地址
   printf("stack variable at: %p\n", &local_var);
   printf("libc function at: %p\n", &system);
   ```

2. **Partial Overwrite**：
   ```
   如果ASLR随机化位数有限（如20位），可以暴力破解低字节
   例如：已知libc基址的高位，只覆盖低位字节
   ```

3. **Brute Force**：
   ```
   32位系统ASLR熵有限（通常8-16位），可以暴力猜解
   64位系统ASLR熵很高（通常24-28位），暴力破解不现实
   ```

4. **侧信道攻击**：
   ```
   通过CPU缓存、分支预测器等侧信道推断内存布局
   ```

5. **JIT喷射**（浏览器场景）：
   ```
   通过反复分配含有shellcode的JIT代码页，提高命中概率
   ```

### 4.5.2 DEP/NX（Data Execution Prevention / No-eXecute）

**原理**：
将内存页标记为不可执行，防止攻击者在数据区域（栈、堆）执行注入的代码。

**硬件支持**：
- **x86**：NX位（PAE模式）或XD位（Intel）、EVP（AMD）
- **x86-64**：NX位（在页表项的第63位）
- **ARM**：XN（Execute Never）位

**查看程序是否启用了NX**：
```bash
checksec --file=vulnerable_binary
# 或
readelf -l vulnerable_binary | grep GNU_STACK
# 如果显示 RWE，则NX禁用；如果显示 RW，则NX启用
```

**绕过技术**：

1. **ROP（Return-Oriented Programming）**：
   ```
   不注入新代码，而是重用现有代码（gadgets）
   gadget = 一小段以ret结尾的指令序列
   
   示例gadget（x86-64）：
   pop rdi; ret
   pop rsi; ret
   pop rdx; ret
   /bin/sh字符串地址
   system()函数地址
   ```

2. **JOP（Jump-Oriented Programming）**：
   ```
   类似ROP，但使用jmp/loop等指令而不是ret
   ```

3. **ret2libc**：
   ```
   直接返回到libc中的函数（如system()）
   需要泄露libc地址
   ```

4. **ret2plt**：
   ```
   返回到PLT中的函数存根
   ```

**ROP示例**：

```bash
# 假设我们要执行 system("/bin/sh")

# 构造ROP链
payload = ""
payload += "A" * 72              # 填充缓冲区
payload += pop_rdi_ret           # gadget: pop rdi; ret
payload += bin_sh_addr           # "/bin/sh"字符串地址
payload += system_addr           # system()函数地址
payload += ret_addr              # 可选的返回地址

# 当vulnerable函数返回时，执行流：
# 1. 弹出bin_sh_addr到RDI
# 2. 返回到system()
# 3. system("/bin/sh")被执行
```

### 4.5.3 PIE（Position Independent Executable）与PIC（Position Independent Code）

**PIC（位置无关代码）**：
- 共享库（.so）必须使用PIC，以便加载到任意地址
- 通过GOT（Global Offset Table）和PLT（Procedure Linkage Table）访问全局符号

**PIE（位置无关可执行文件）**：
- 可执行文件本身也是位置无关的
- 需要ASLR配合随机化可执行文件基址
- 编译时启用：`-fpie -pie`

**查看是否启用PIE**：
```bash
file vulnerable_binary
# 如果显示 "pie executable"，则启用了PIE

readelf -h vulnerable_binary | grep Type
# EXEC = 未启用PIE
# DYN = 启用PIE
```

**绕过技术**：

1. **信息泄露**：
   ```
   泄露任意代码地址，计算基址偏移
   例如：通过格式化字符串泄露main()地址
   ```

2. **Partial Overwrite**：
   ```
   如果PIE随机化范围有限（如低12位不变），可以部分覆盖
   ```

3. **已知偏移**：
   ```
   如果泄露了一个函数地址，可以计算其他函数的地址
   libc_base = leaked_addr - offset_of_leaked_function_in_libc
   system_addr = libc_base + offset_of_system_in_libc
   ```

### 4.5.4 RELRO（RELocation Read-Only）

**原理**：
保护GOT（Global Offset Table）不被篡改。

**两种模式**：

1. **Partial RELRO**（部分RELRO）：
   - GOT写在数据段（可读写）
   - 但GOT的一部分（.got.plt）在加载时解析后设为只读
   - 编译默认启用：`-Wl,-z,relro`

2. **Full RELRO**（完全RELRO）：
   - 所有重定位在程序启动前完成（禁用lazy binding）
   - GOT完全只读
   - 编译启用：`-Wl,-z,relro,-z,now`

**查看RELRO状态**：
```bash
checksec --file=vulnerable_binary
# Partial RELRO 或 Full RELRO
```

**绕过技术**（Partial RELRO下）：
- 修改GOT条目，重定向函数调用
- 例如：将`strlen()`的GOT项修改为`system()`的地址

### 4.5.5 Stack Canary（已在4.3.4介绍）

### 4.5.6 其他保护机制

1. **FORTIFY_SOURCE**：
   ```
   编译时替换危险函数（如memcpy → __memcpy_chk）
   运行时检查缓冲区溢出
   启用：-D_FORTIFY_SOURCE=2
   ```

2. **GCC的指针保护**：
   ```
   -vtable-verify：验证C++虚函数表指针
   ```

3. **KALSR（Kernel ASLR）**：
   ```
   内核地址空间随机化
   ```

4. **SMAP/SMEP（x86-64）**：
   ```
   SMAP（Supervisor Mode Access Prevention）：禁止内核访问用户态内存
   SMEP（Supervisor Mode Execution Prevention）：禁止内核执行用户态代码
   ```

## 4.6 CPU缓存侧信道攻击

### 4.6.1 侧信道攻击基础

**侧信道攻击（Side-Channel Attack）**：
通过测量系统的物理实现（时间、功耗、电磁辐射等）来推断敏感信息，而不是直接攻击算法本身。

**CPU缓存侧信道**：
利用CPU缓存的访问时间差异来推断内存访问模式，从而获取敏感数据。

**CPU缓存层次结构**（典型x86-64）：
```
CPU → L1 Cache (32KB, ~4 cycles)
    → L2 Cache (256KB, ~12 cycles)
    → L3 Cache (8MB, ~40 cycles)
    → RAM (几GB, ~200 cycles)
```

**关键观察**：
- 访问缓存中的数据：快（几个CPU周期）
- 访问内存中的数据：慢（几百个CPU周期）
- 通过精确测量访问时间，可以推断数据是否在缓存中

### 4.6.2 Flush+Reload 攻击

**原理**：
1. **Flush**：使用`clflush`指令将目标内存行从所有缓存中清除
2. **等待**：受害者进程访问该内存行（或不访问）
3. **Reload**：攻击者测量访问该内存行的时间
   - 如果快：受害者访问了该内存行
   - 如果慢：受害者没有访问

**适用场景**：
- 攻击者与受害者共享内存（如共享库）

**代码示例**（简化）：

```c
// 攻击者代码
void flush_reload_attack(void *target_addr) {
    int i;
    uint64_t time1, time2;
    
    for (i = 0; i < 1000; i++) {
        // 1. Flush：清除缓存
        _mm_clflush(target_addr);
        mfence();  // 内存屏障
        
        // 2. 等待受害者执行
        usleep(100);
        
        // 3. Reload：测量访问时间
        time1 = rdtsc();  // 读取时间戳计数器
        dummy = *(volatile int *)target_addr;
        time2 = rdtsc();
        
        if (time2 - time1 < CACHE_HIT_THRESHOLD) {
            printf("Victim accessed target address!\n");
        }
    }
}
```

### 4.6.3 Spectre 攻击

**Spectre v1：边界检查绕过（Bounds Check Bypass）**

**原理**：
利用CPU的**推测执行（Speculative Execution）**特性，在分支预测错误时，CPU会回滚执行结果，但**不会回滚缓存状态**。

**攻击步骤**：

```c
// 受害者代码（有边界检查漏洞）
struct array {
    unsigned long length;
    unsigned char data[];
};

unsigned char victim_function(struct array *arr, unsigned long idx) {
    if (idx < arr->length) {  // 边界检查
        return arr->data[idx];  // 如果idx越界，会访问非法地址
    }
}

// 攻击者代码
void spectre_attack(void *target_addr) {
    // 1. 训练分支预测器：让CPU认为idx < arr->length总是成立
    for (i = 0; i < 100; i++) {
        victim_function(arr, i);
    }
    
    // 2. 恶意idx：越界，但CPU推测执行会先执行它
    unsigned long malicious_idx = arr->length + 10;
    
    // 3. 触发推测执行：CPU会先执行 arr->data[malicious_idx]
    //    虽然最终会发现越界并回滚，但在回滚前，数据已经被加载到缓存
    victim_function(arr, malicious_idx);
    
    // 4. 通过Flush+Reload读取target_addr的内容
    //    （因为推测执行时，arr->data[malicious_idx]的值被用作读取某个地址的索引）
}
```

**Spectre v2：分支目标注入（Branch Target Injection）**

利用**间接分支预测器**，诱导受害者执行攻击者选择的gadget。

### 4.6.4 Meltdown 攻击

**原理**：
利用**乱序执行（Out-of-Order Execution）**，在CPU执行异常处理之前，先执行了非法的内存读取（如读取内核内存）。

**攻击步骤**：

```c
// 攻击者代码
void meltdown_attack(void *kernel_addr) {
    unsigned char *probe_array = malloc(256 * 4096);
    
    // 1. 加载内核地址（会触发异常，但CPU会乱序执行后面的指令）
    unsigned char kernel_value = *(unsigned char *)kernel_addr;
    
    // 2. 乱序执行：用内核值作为索引访问probe_array
    //    （此时kernel_value已经在CPU寄存器中）
    unsigned char temp = probe_array[kernel_value * 4096];
    
    // 3. 异常处理：CPU最终会回滚，但probe_array的某一页已经在缓存中
    
    // 4. 通过Flush+Reload确定kernel_value的值
    for (i = 0; i < 256; i++) {
        if (reload_time(&probe_array[i * 4096]) < CACHE_HIT_THRESHOLD) {
            printf("Kernel value: 0x%02x\n", i);
            break;
        }
    }
}
```

**区别**：
- **Spectre**：利用**推测执行**，影响几乎所有现代CPU，较难修复
- **Meltdown**：利用**乱序执行**，主要影响Intel CPU（AMD和ARM不受影响），可通过KPTI修复

### 4.6.5 防御措施

1. **软件补丁**：
   - **KPTI（Kernel Page Table Isolation）**：隔离内核页表和用户页表，防止Meltdown
   - **Retpoline**：用return指令替换间接分支，防止Spectre v2

2. **硬件修复**：
   - 新CPU加入**IBRS（Indirect Branch Restricted Speculation）**
   - **STIBP（Single Thread Indirect Branch Predictors）**
   - **SSBD（Speculative Store Bypass Disable）**

3. **编译器支持**：
   ```
   gcc -mindirect-branch=thunk  # 启用Retpoline
   ```

### 4.7.3 编写简单的内存布局打印程序

**程序代码**：

```c
// mem_layout.c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

// 全局变量
int global_init = 42;         // .data
int global_uninit;            // .bss

int main() {
    // 局部变量（栈）
    int local_var = 100;
    printf("Stack:      %p\n", &local_var);
    
    // 堆
    void *heap_var = malloc(32);
    printf("Heap:       %p\n", heap_var);
    free(heap_var);
    
    // 代码段
    printf("Code (.text): %p\n", &main);
    
    // 数据段
    printf(".data:      %p\n", &global_init);
    printf(".bss:       %p\n", &global_uninit);
    
    // 共享库
    printf("libc:       %p\n", &puts);
    
    // 通过/proc/self/maps查看完整布局
    printf("\nFull memory map: /proc/self/maps\n");
    char cmd[256];
    snprintf(cmd, sizeof(cmd), "cat /proc/%d/maps", getpid());
    system(cmd);
    
    return 0;
}
```

**编译与运行**：

```bash
# 32位
gcc -m32 -o mem_layout32 mem_layout.c
./mem_layout32

# 64位
gcc -o mem_layout64 mem_layout.c
./mem_layout64

# 启用PIE
gcc -fpie -pie -o mem_layout_pie mem_layout.c
./mem_layout_pie
```

**观察输出**：
- 各段地址的相对位置
- 启用ASLR后，每次运行堆/栈/libc地址都不同
- 启用PIE后，代码段地址也随机化

## 4.8 本章小结

本章深入探讨了计算机体系结构与内存模型，这是漏洞挖掘的基础。主要内容包括：

1. **虚拟内存管理机制**：
   - 分页机制（32位两级页表、64位四级页表）
   - TLB的作用与侧信道意义
   - 页表遍历过程与CR3寄存器

2. **进程内存布局**：
   - 代码段、数据段、BSS段、堆、栈的位置与权限
   - 32位与64位布局的差异
   - 使用/proc和GDB查看内存布局

3. **栈帧结构与函数调用**：
   - x86-32与x86-64的调用约定
   - 栈溢出的原理与利用
   - Stack Canary的保护与绕过

4. **堆内存管理**：
   - ptmalloc2的堆块结构
   - fastbin/smallbin/largebin/tcache的管理
   - 堆溢出、UAF、double free等漏洞

5. **现代内存保护机制**：
   - ASLR：地址随机化，需信息泄露绕过
   - DEP/NX：数据执行保护，需ROP绕过
   - PIE/PIC：位置无关代码，需信息泄露绕过
   - RELRO：GOT保护
   - 各种保护的组合与权衡

6. **CPU缓存侧信道攻击**：
   - Spectre v1/v2：利用推测执行
   - Meltdown：利用乱序执行
   - Flush+Reload等技术
   - 软件与硬件防御措施

7. **实战演练**：
   - 使用checksec分析二进制保护
   - 使用GDB验证内存布局
   - 编写程序观察内存布局

**关键要点**：

- 理解内存布局是漏洞利用的基础
- 现代系统的保护机制是**深度防御（Defense in Depth）**，单一保护容易被绕过，但组合使用大幅提高了攻击难度
- 侧信道攻击展示了**体系结构层面**的漏洞，难以通过软件完全修复
- 实战中需要**信息泄露**配合，才能绕过ASLR、PIE等保护

## 4.9 思考题

### 基础题

1. **虚拟内存**：
   - 为什么需要虚拟内存？它如何提供进程隔离？
   - 32位系统使用4KB页面，那么页表本身占用多少内存？

2. **分页机制**：
   - x86-64的4级页表，虚拟地址到物理地址的转换需要几次内存访问？如果TLB命中呢？
   - 什么是Huge Pages？它有什么优缺点？

3. **内存布局**：
   - 为什么栈向低地址增长，而堆向高地址增长？
   - BSS段和.data段有什么区别？为什么需要区分？

### 进阶题

4. **栈保护**：
   - Stack Canary是如何生成的？它存储在哪里？
   - 如果程序有格式化字符串漏洞，如何泄露Canary？

5. **堆管理**：
   - fastbin为什么不合并空闲块？这会带来什么安全问题？
   - tcache的引入解决了什么问题？又引入了哪些新的利用方式？

6. **ASLR**：
   - 32位系统和64位系统的ASLR强度有何差异？为什么？
   - 如果程序泄露了一个栈地址，如何计算其他栈变量的地址？

7. **DEP/NX与ROP**：
   - 编写一个简单的ROP chain，调用`system("/bin/sh")`（x86-64）
   - ROP有什么局限性？（提示：payload大小、ASLR、信号机制等）

### 挑战题

8. **侧信道攻击**：
   - Spectre v1利用了CPU的什么特性？为什么这个特性会导致安全问题？
   - Meltdown为什么主要影响Intel CPU？AMD和ARM是如何防止的？

9. **综合**：
   - 给定一个开启了所有保护的二进制（ASLR、NX、PIE、Canary、RELRO），你需要哪些原语（primitives）才能成功利用？
   - 设计一个漏洞利用方案，要求：信息泄露 → 绕过ASLR/PIE → 控制执行流 → 执行shellcode

10. **研究**：
    - 除了本章介绍的，还有哪些内存保护机制？（提示：Intel CET、ARM MTE、PaX等）
    - 近年来有哪些新的侧信道攻击？（提示：L1TF、MDS、Spectre-NG等）
