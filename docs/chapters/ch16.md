## 16.1 漏洞披露原则

### 16.1.1 披露类型

| 类型 | 说明 | 优缺点 |
|------|------|----------|
| **全披露**（Full Disclosure） | 立即公开漏洞详情 + PoC | ✅ 推动供应商修复<br>❌ 易被攻击者利用 |
| **负责任披露**（Responsible Disclosure） | 先通知供应商，限期修复后公开 | ✅ 给予修复时间<br>❌ 供应商可能拖延 |
| **不披露**（Non-Disclosure） | 不公开（如军事漏洞） | ✅ 避免危害<br>❌ 无法推动修复 |
| **0day 销售**（0day Brokerage） | 出售给政府/公司 | ✅ 获得报酬<br>❌ 道德争议 |

### 16.1.2 负责任披露流程

```
发现漏洞 → 验证漏洞 → 编写报告 → 通知供应商 → 
协调修复 → 公开披露 → 归档
```

**时间线**：

| 阶段 | 时间 | 说明 |
|------|------|------|
| 通知供应商 | Day 0 | 发送初始报告 |
| 供应商确认 | Day 7 | 供应商确认漏洞 |
| 补丁开发 | Day 30~90 | 供应商开发补丁 |
| 补丁测试 | Day 91~100 | 测试补丁有效性 |
| 公开披露 | Day 101 | 发布漏洞详情 |
| **总时限** | **90~120 天** | 如供应商超时，可公开 |

## 16.2 编写漏洞报告

### 16.2.1 报告结构

**标准格式**：

```markdown
# 漏洞报告：<漏洞标题>

## 1. 基本信息
- **发现者**：<你的名字/昵称>
- **发现日期**：YYYY-MM-DD
- **供应商**：<公司/项目名>
- **产品版本**：<受影响版本>
- **漏洞类型**：<SQL 注入/XSS/缓冲区溢出/...>
- **危害等级**：<Critical/High/Medium/Low>

## 2. 漏洞描述
<用 1-2 段话描述漏洞原理>

## 3. 复现步骤
1. <步骤1>
2. <步骤2>
3. <步骤3>

## 4. PoC（概念验证）
<提供漏洞利用代码/截图/视频>

## 5. 危害评估
- **CVE 编号**：<如已申请>
- **CVSS 评分**：<如已知>
- **潜在危害**：<数据泄露/代码执行/DoS/...>

## 6. 修复建议
1. <建议1>
2. <建议2>

## 7. 时间线
- YYYY-MM-DD：发现漏洞
- YYYY-MM-DD：通知供应商
- YYYY-MM-DD：供应商确认
- YYYY-MM-DD：补丁发布

## 8. 联系方式
- **邮箱**：<你的邮箱>
- **GPG 公钥**：<如需要加密通信>
```

### 16.2.2 编写要点

**1. 清晰简洁**
- ✅ 使用列表、表格、代码块
- ❌ 避免冗长段落

**2. 提供 PoC**
- ✅ 提供完整 PoC（代码/截图/视频）
- ❌ 避免仅描述理论

**3. 评估危害**
- ✅ 使用 CVSS v3.1 评分
- ✅ 说明实际危害（如数据泄露、RCE）

**4. 给出修复建议**
- ✅ 提供具体修复方案（如代码补丁）
- ❌ 避免仅说"修复漏洞"

### 16.2.3 示例报告

```markdown
# 漏洞报告：SQL 注入 in WordPress Plugin X (CVE-2023-12345)

## 1. 基本信息
- **发现者**：VulnResearcher
- **发现日期**：2023-05-15
- **供应商**：WordPress Plugin X 开发团队
- **产品版本**：Plugin X <= 2.1.3
- **漏洞类型**：SQL 注入（Time-based Blind）
- **危害等级**：High (CVSS 8.6)

## 2. 漏洞描述
WordPress Plugin X 的 `search.php` 文件未过滤用户输入，
导致攻击者可以注入恶意 SQL 语句，获取数据库敏感信息。

## 3. 复现步骤
1. 访问 `http://target.com/wp-content/plugins/x/search.php?q=test`
2. 注入 payload：`test' AND (SELECT 1 FROM (SELECT sleep(5))a)-- `
3. 观察响应时间是否 >5 秒

## 4. PoC
```python
import requests
import time

url = "http://target.com/wp-content/plugins/x/search.php?q="
payload = "test' AND (SELECT 1 FROM (SELECT sleep(5))a)-- "

start = time.time()
r = requests.get(url + payload)
end = time.time()

if end - start > 5:
    print("Vulnerable!")
```

## 5. 危害评估
- **CVE 编号**：CVE-2023-12345
- **CVSS 评分**：8.6 (High)
- **潜在危害**：攻击者可以获取管理员密码、修改数据

## 6. 修复建议
1. 使用预处理语句（Prepared Statements）
2. 输入验证（白名单）
3. 限制数据库用户权限

## 7. 时间线
- 2023-05-15：发现漏洞
- 2023-05-16：通知供应商
- 2023-05-20：供应商确认
- 2023-06-10：补丁发布（v2.1.4）

## 8. 联系方式
- **邮箱**：vulnresearcher@example.com
- **GPG 公钥**：https://keys.openpgp.org/...
```

## 16.3 申请 CVE 编号

### 16.3.1 CVE 简介

**CVE**（Common Vulnerabilities and Exposures）是公开的漏洞数据库，每个漏洞分配唯一编号。

**格式**：`CVE-YYYY-NNNN`
- `YYYY`：年份
- `NNNN`：序号（至少 4 位）

**示例**：`CVE-2023-12345`

### 16.3.2 申请流程

**方法1：通过 MITRE（官方）**

1. 访问 https://cveform.mitre.org/
2. 填写表单（漏洞详情、PoC、影响）
3. 等待审核（1-2 周）
4. 接收 CVE 编号

**方法2：通过 CNA（CVE Numbering Authority）**

**常见 CNA**：
- **GitHub**：https://github.com/security/advisories
- **GitLab**：https://gitlab.com/-/security/advisories
- **Google**：https://bughunter.withgoogle.com/
- **Microsoft**：https://msrc.microsoft.com/

**步骤**：
1. 在 GitHub 创建 Security Advisory
2. 填写漏洞详情
3. 请求 CVE 编号
4. 等待审核（1-3 天）

### 16.3.3 编写 CVE 描述

**标准格式**：

```markdown
# CVE-2023-12345

## Description
WordPress Plugin X <= 2.1.3 is vulnerable to SQL injection 
via the `q` parameter in `search.php`. An attacker can 
extract sensitive information from the database.

## CVSS v3.1 Score
**Base Score**: 8.6 (High)
**Vector**: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:L

## References
- **PoC**: https://github.com/.../CVE-2023-12345
- **Patch**: https://plugins.trac.wordpress.org/.../changeset/12345/

## Timeline
- 2023-05-15：Discovered
- 2023-05-16：Reported to vendor
- 2023-06-10：Patch released
- 2023-06-15：Public disclosure
```

## 16.4 与供应商协调

### 16.4.1 沟通要点

**1. 使用加密通信**
- ✅ 使用 GPG 加密邮件
- ✅ 使用 Signal/WhatsApp（端到端加密）

**2. 提供完整信息**
- ✅ 提供漏洞报告（见 16.2）
- ✅ 提供 PoC 和利用脚本

**3. 设定截止日期**
- ✅ 给予 90 天修复时间
- ✅ 如超时，提前通知将公开

### 16.4.2 应对拖延的供应商

**场景1：供应商不回复**

**应对**：
1. 等待 7 天，再次发送邮件
2. 等待 14 天，公开声明（不披露详情）
3. 等待 30 天，考虑公开漏洞

**场景2：供应商拒绝修复**

**应对**：
1. 解释危害（提供 CVSS 评分）
2. 提供修复建议（代码示例）
3. 如仍拒绝，公开漏洞（全披露）

**场景3：供应商威胁法律行动**

**应对**：
1. 咨询法律意见（EFF、ACLU）
2. 暂停披露（等待法律结果）
3. 如合法，继续披露

## 16.5 公开披露

### 16.5.1 披露渠道

**1. 学术会议**
- **Black Hat**：https://www.blackhat.com/
- **DEF CON**：https://www.defcon.org/
- **USENIX Security**：https://www.usenix.org/

**2. 邮件列表**
- **Full Disclosure**：http://seclists.org/fulldisclosure/
- **Bugtraq**：https://bugtraq.securityfocus.com/

**3. 漏洞平台**
- **HackerOne**：https://hackerone.com/
- **Bugcrowd**：https://www.bugcrowd.com/
- **OpenBugBounty**：https://www.openbugbounty.org/

**4. 个人博客/GitHub**
- 发布到个人网站
- 发布到 GitHub Advisory

### 16.5.2 披露内容

**应包含**：
- ✅ 漏洞描述
- ✅ 受影响版本
- ✅ 修复版本
- ✅ PoC（非破坏性）
- ✅ CVE 编号

**不应包含**：
- ❌ 完整利用脚本（给予攻击者便利）
- ❌ 目标敏感信息（如真实用户数据）
- ❌ 个人攻击（如辱骂供应商）

### 16.5.3 时间线示例

```
Day 0：发现漏洞
Day 1：通知供应商（发送报告）
Day 7：供应商确认
Day 30：供应商提供补丁（测试版）
Day 60：补丁测试完成
Day 90：补丁正式发布
Day 91：公开披露（发布博客 + CVE）
```
